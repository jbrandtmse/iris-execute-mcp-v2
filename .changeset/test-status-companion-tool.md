feat(test-status): `iris_test_status` companion tool — re-attach, read-by-runIndex, cancel (Story 36.2)

Epic 36's only new tool (dev 28 → 29): the re-attach/read/cancel companion Story 36.1 documented as a seam and this story ships. Re-attach to a run `iris_execute_tests` reported `status: "running"` for (or that your own client abandoned) instead of re-submitting the same target, which starts a SECOND concurrent run against shared fixtures.

`action: "poll"` (read, enabled by default) accepts `jobId` and/or `runIndex`. By `jobId`: the queue node's run index is read BEFORE any poll that could be terminal (a terminal poll — or a `cancel` — consumes it, probe (b)); while `Retry-After` is present it returns the SAME `status: "running"` shape `iris_execute_tests` builds (through the identical shared `testRunEnvelope` helper, exported and reused rather than copied — Rule #52), with `partial` carrying THIS poll's DELTA drain only, never cumulative across separate calls. Once finished, the completed envelope is built AUTHORITATIVELY from `%UnitTest_Result` by exact `InstanceIndex` (`runIndexSource: "result-table"`) — never from a single drain alone: an earlier `iris_execute_tests` "running" response may already have consumed some rows, which never reappear (probe (d)). A `jobId` Atelier no longer recognizes (HTTP 404) falls back to a supplied `runIndex`, else reports a clear not-found result naming that fallback. By `runIndex` alone: `status: "completed"` (the same SQL path) once `TestInstance.DateTime` is set, or `status: "unfinished"` when it is not — the result table alone cannot distinguish a still-running job from a cancelled/crashed one (a cancelled run's row never finishes, probe (e)), so `unfinished` carries interim rows only under `partial`, each explicitly labelled `"in-progress"` and excluded from the counts (never reported as a pass — a mid-run `TestMethod` row reads `Status 1`/`Duration 0` before the method actually finishes, the trap the Story 36.1 review found in the manual SQL route). A `jobId` whose queue node is gone AND whose `runIndex` shows unfinished is reported `status: "abandoned"`.

`action: "cancel"` (write, DEFAULT-DISABLED — enable via `IRIS_GOVERNANCE`, e.g. `{"global":{"iris_test_status:cancel":true}}`) stops a RUNNING job (`DELETE /work/{jobId}`, reading the queue node's run index BEFORE the delete — the only chance to) and reports the OBSERVED outcome, never assumed: `status: "cancelled"` with what was actually seen (queue entry gone; result row never finalized), or, when the job had ALREADY finished but was never drained, `status: "completed"` with a note that cancelling discarded only the queue entry and results are preserved at that `runIndex`. `cancel` requires `jobId` (there is no way to cancel by `runIndex` alone — the Atelier work-queue `DELETE` route operates on the job id).

A Task 1 live probe found the normalization this story's SQL-path builder depends on: `%UnitTest_Result.TestMethod.Duration` is recorded in SECONDS (its class doc says so) while the Atelier drain's `duration` field (what `iris_execute_tests`'s `details` already carries) is in MILLISECONDS — verified live with a real 10-second `Hang` (drain `10009.384` vs. SQL `10.009384`, an exact ×1000). The SQL-path builder converts it to the drain's exact milliseconds (an integer-microsecond scale then one division — a plain float `* 1000` is not exact), and also carries the drain's method-level error text (e.g. a thrown exception) and row order, so its `completed` envelope is VALUE-identical to the drain-path one for the same run — pinned by unit tests on live captures and by the live capstone's exact drain-path equality leg (`ExecuteMCPv2.QAFixtures.DeltaDrainTest`). A finished run with no method-level results returns the same `isError: true` zero-result guard `iris_execute_tests` does.

`iris_execute_tests`'s own `hint` (on a `running`/error result) and description now name `iris_test_status` as the primary re-attach route, alongside the manual `iris_global_get` + `iris_sql_execute` route that still works in every preset (including `core`, which does not include the new tool — Lead decision L-2: `core` is already at its 13-runtime-tool ceiling).

**Governance:** two new post-foundation keys, `iris_test_status:poll` (read, enabled) and `iris_test_status:cancel` (write, disabled) — the frozen Epic-14 baseline (`1e62c5ad5bf7`, 141 keys) is unchanged (203 live / 62 post-foundation). **Visibility:** `developer`-preset include, `core`-preset exclude; NOT a `TOOL_PAIRS` member. Tool counts: dev 28 → 29; suite `full` 104/109 → 105/110 (package/advertised), `developer` 76/81 → 77/82, `core` unchanged (49/54).

**Back-compat (Rule #19):** `iris_execute_tests`'s output shapes and full pre-existing test suite are unchanged; only its `hint` and description text changed (they now name `iris_test_status`, with the run's namespace). The shared envelope builder's extension — new `unfinished`/`abandoned`/`cancelled` discriminator cases, optional wait-budget-context fields on `running` (`elapsedMs`/`timeoutMs`/`target`/`level`/`namespace`, which a re-attach poll has no way to know and never fabricates), and an optional `note` on `completed` — is strictly additive; `iris_execute_tests` always supplies every field it always supplied, so its own output is unaffected.

Live-gated: a default-suite capstone (`test-status-epic-gate.test.ts`, armed on the packaging path by the dev `prepublish-gate.mjs`, which runs it with `IRIS_REQUIRE_LIVE=1`) drives the full round trip over real HTTP against a real IRIS instance — submit → running → poll-while-running → poll-completed (equal to an independent live SQL oracle) → queue node gone → poll-by-runIndex-alone → a cancel leg through the REAL governance gate (denied by default, observed still running; enabled via a process-local `IRIS_GOVERNANCE` override, then observed PAST the run's natural finish time and still unfinished) — plus a delta-drain leg proving the `completed` envelope carries every method after `iris_execute_tests` already drained some, with rows exactly equal to the drain path's. Second-instance smoke run against `ocupilot-iris` (disposable fixture, deleted after).
