fix(execute): decode non-ASCII request-body content correctly instead of silently corrupting it (Story 34.8, ledger `34-6-CR-7`)

**The defect.** Every custom `ExecuteMCPv2.REST.*` handler read its JSON request body through the shared `ExecuteMCPv2.Utils.ReadRequestBody` helper (14 handler classes, 46 call sites, spanning all five servers), which handed the raw POST body straight to `%DynamicObject.%FromJSON()` with no UTF-8 decode. Non-ASCII characters submitted through a request body arrived mis-decoded as their raw UTF-8 bytes read as Latin-1 — `é` (U+00E9) as two garbled characters, `世界` as six, an emoji as four — silently, with `HTTP 200` and no error or truncation flag. This affected `iris_execute_command`'s `command`, `iris_execute_classmethod`'s `args`, and — most seriously — `iris_global_set`'s `value`, where the corrupted text was written to the target global as genuine **data corruption at rest**. Content that originates server-side (e.g. a compiled class's literal source) was always unaffected; the defect was strictly on the inbound request-body path. Story 34.7 documented this as a Known Limitation rather than fix it before the first publish; the Project Lead elected to fix it before publishing rather than ship documented data corruption.

**Root cause, live-probed (AC 34.8.1) rather than guessed.** `%request.GetMimeData("BODY")` is never populated for this project's plain `application/json` POSTs (multipart-only) — the primary branch in `ReadRequestBody` was dead in practice; every real call fell through to the `%request.Content` fallback, a `%CSP.BinaryStream` holding the raw, untranslated request bytes (confirmed byte-for-byte against a known UTF-8 encoding). `%request.CharSet` is empty because the TS client's `Content-Type: application/json` header carries no charset parameter, so no CSP-level charset negotiation ever applied.

**The fix.** `ReadRequestBody` now routes the resolved stream through a new `ExecuteMCPv2.Utils.DecodeUtf8Stream`, which decodes the raw bytes as UTF-8 before handing the result to `%FromJSON`. Two properties, both required by the ACs and both mechanically pinned:

- **Chunk-boundary safety.** Reads the stream in bounded chunks (1,000,000 raw bytes at a time) and detects, via a new `IncompleteUtf8TailLength` helper, whether the trailing 0-3 bytes of a chunk are the unfinished start of a multi-byte sequence — holding them back and prepending them to the next chunk rather than decoding a split sequence independently (the naive-per-chunk-`$ZCONVERT` trap). Live-verified with a deliberately tiny chunk size against content containing 2-, 3-, and 4-byte UTF-8 characters back to back, and swept across every possible chunk size for a representative fixture.
- **Large-body safety, with two traps found live rather than assumed.** (1) `$ZCONVERT` given a stream OREF directly — rather than a materialized `%String` chunk — does not throw and does not decode: it silently stringifies the OREF itself. (2) A single `.Read(stream.Size)` call requesting an entire large stream's content in one shot does not reliably return it all: measured on a 49,000,000-byte stream, one such call silently returned only ~3.6 million characters, with **no exception of any kind** — never `<MAXSTRING>`, just quietly less data than requested. The fix reads in a `While 'stream.AtEnd` loop and accumulates DECODED output into a `%Stream.TmpCharacter` (never a growing `%String`), verified end-to-end at 49,000,000 raw bytes with zero exceptions and a correct content spot-check.

**Back-compat (Rule #19), proven mechanically.** Pure-ASCII request-body content — every one of this suite's pre-existing ObjectScript command / classmethod-arg / global-value calls — is byte-for-byte identical before and after the fix (every ASCII code point 0-127 is already valid single-byte UTF-8, so the decode is a true no-op on ASCII). Pinned both at the ObjectScript unit level (`ExecuteMCPv2.Tests.Utf8DecodeTest`, 33 tests) and end-to-end against the real deployed `/command`/`/classmethod`/`/global` routes (`request-body-utf8-decode.test.ts`, 12 tests) — the latter also covers accented BMP, CJK, astral-plane emoji, mixed ASCII+non-ASCII, non-ASCII inside a `{byRef, value}` marker, a non-ASCII JSON key alongside real content, and the exact live reproduction string reported for this defect. Mutation-verified at both layers: reverting the fix reproduces the original mojibake live and turns both test files red; restoring it (byte-identical to the committed source) turns them green again.

**QA follow-up fix, same story: malformed input could produce genuinely invalid UTF-8 on a response.** Adversarial QA testing found that `$ZCONVERT(...,"I","UTF8")` is lenient enough to decode a malformed 3-byte WTF-8/CESU-8 byte sequence (`0xED [0xA0-0xBF] [0x80-0xBF]` — never valid in conformant UTF-8, since RFC 3629 excludes the whole surrogate block from UTF-8) into a raw, unpaired UTF-16 surrogate code unit rather than rejecting it. The pre-Story-34.8 Latin-1 decode this replaced could never produce a surrogate from any input, so this was a new failure mode introduced by the UTF-8-aware decode, not a pre-existing one. Live-verified with a hand-crafted raw HTTP body (bypassing the sanitization any standard JSON+UTF-8 client, including this suite's own `IrisHttpClient`, always performs before such a byte pattern could reach the wire): an unpaired surrogate reaching a response was re-emitted by IRIS as genuinely invalid UTF-8 — a strict decoder threw on the actual response bytes, silently, under `HTTP 200`, no error, no truncation flag — the same underlying platform behavior Story 34.7's `SurrogateSafeCutLength` already guards against on the truncation/output side. Fixed with a new `ExecuteMCPv2.Utils.SanitizeUnpairedSurrogates` helper, applied to every decoded chunk, that substitutes `?` for any surrogate half without a valid pairing partner (matching `$ZCONVERT`'s own observed substitution for other invalid sequences) while leaving every genuine surrogate pair (real astral characters) completely untouched. Re-verified live after the fix: the same hand-crafted request now round-trips to a strictly-valid-UTF-8 response. Not reachable through any of this suite's own MCP tool clients — only through a hand-crafted raw HTTP body — but fixed rather than left as a new, undocumented gap, consistent with this epic's standing policy against shipping a silent-corruption path under `HTTP 200`.

**The decoder is lenient, not validating — and that is now documented for users.** Beyond the unpaired-surrogate case above, two further malformed-input dispositions were determined live and pinned, and are stated in both READMEs' "Known Limitations" sections rather than left in code comments only: (1) any invalid byte sequence — an orphan continuation byte, an out-of-range lead byte, a truncated sequence at end of body — is replaced with a literal `?` under `HTTP 200` rather than rejected, and that `?` is indistinguishable from one the caller genuinely sent; (2) non-canonical **overlong** encodings are decoded rather than refused (e.g. the bytes `0xC0 0xAF` decode to `/`, which conformant UTF-8 per RFC 3629 forbids). (2) carries a **security note** now published in the suite README: overlong forms are a classic filter-bypass technique, so any proxy/WAF/gateway rule placed in front of these endpoints that inspects **raw bytes** for characters like `/`, `.`, or a quote can be bypassed by an overlong encoding that still decodes to the canonical character inside IRIS — such rules must normalize UTF-8 themselves. This matters because these endpoints execute arbitrary ObjectScript and write globals. Well-formed input is never affected by either behavior.

**The fix is forward-only.** It corrects decoding for requests received after it is deployed; it does not repair data already written corrupted while the defect was live (e.g. a global populated via `iris_global_set` before upgrading). There is no automated repair tool for previously-corrupted data — documented explicitly in both READMEs' "Known Limitations" sections.

No new tool, no new governance key, no tool-count change (Rule #31) — this is a fix to existing, already-governed request handling.
