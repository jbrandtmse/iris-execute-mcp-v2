feat(execute): bound `iris_execute_command`/`iris_execute_classmethod` response payloads, make the epic gate fail closed, and make the zero-result guard machine-detectable (Story 34.6, pre-publish hardening)

**Response payload ceiling (AC 34.6.1, `34-2-R2`/`34-3-R2`).** `output` on both `/command` and `/classmethod` is now capped at 32768 characters (`ExecuteMCPv2.Utils.OUTPUTCEILING`) — content beyond the ceiling is cut off and replaced with a structured, machine-detectable elision marker (`[IRIS-MCP-TRUNCATED ceiling=32768chars]`), never a bare `...`. `truncated` folds this in alongside the pre-existing capture-overflow signal (only ever set, never cleared, so the two causes OR together). `iris_execute_classmethod`'s `byRefValues` gains its own combined 1000-node (`ExecuteMCPv2.Utils.BYREFNODECEILING`) / 32768-character budget shared across every marked position, surfaced via a new additive `byRefTruncated` boolean — reported separately from `truncated` since they describe different response fields. A cut-off node in `byRefValues` is marked `subscriptsTruncated: true`.

The ceiling was picked from live measurement (Rule #36), not by feel: the CSP Gateway/HTTP transport tolerates multi-megabyte responses cleanly (tested clean to 3,000,000 characters over `/command`), so **this is explicitly not protection against a Web Gateway timeout or the target's own execution cost** (Rule #38) — the target has already fully run by the time the ceiling is applied. 32768 was chosen because a real, live MCP client (Claude Code CLI, this repo's own dev environment) was observed diverting a rendered tool result away from inline consumption once it reached 50,031 characters; 32768 stays safely under that measured boundary. Note the ceiling is applied PER FIELD (`output`, `returnValue`, and the `byRefValues` budget each get their own), so it bounds any one field comfortably but does not bound the whole envelope — a response carrying all three at once is roughly three times that figure before JSON escaping.

**Back-compat (Rule #19), proven mechanically:** under-ceiling responses on both endpoints are byte-identical to today's shape (live HTTP + `%UnitTest` pins); `byRefTruncated` is additive and simply absent — never `false` — from a pre-34.6 envelope shape.

**`returnValue` is now ALSO bounded (code-review finding CR-5, review-continuation pass).** The ceiling above covered `output` and `byRefValues` but not `returnValue` — the PRIMARY payload field on `/classmethod` — so a target returning a large string shipped fully unbounded, defeating the ceiling's own stated purpose (a live 1,000,000-character `returnValue` shipped with `truncated:false`). `returnValue` is now capped at the same 32768 characters with the same elision marker, flagged via a new additive `returnValueTruncated` boolean (symmetric with `truncated`/`byRefTruncated`, present — defaulted false — on both error envelopes too). Pinned at the REAL deployed `/classmethod` endpoint (a new leg in the epic-gate file, not a re-implementation), mutation-verified RED when the fix is removed. **Back-compat (Rule #19):** under-ceiling `returnValue` is byte-identical; `returnValueTruncated` is additive and absent (not `false`) from a pre-fix envelope.

**The `byRefValues` byte budget no longer destroys small values with oversized markers (code-review finding CR-6, review-continuation pass — a defect this story itself introduced, not pre-existing).** Once one large `Output` value exhausted the shared byte budget, every later marked position was still truncated — and when the remaining budget was smaller than the ~37-character elision marker itself, that truncation replaced a small real value with a marker LARGER than the value it destroyed (live repro: `"42"`, `"hello"`, `"x"` became 37-character markers), pushing the total past the documented 32768-character budget. Fixed in two places: `ApplyOutputCeiling` now falls back to a plain, marker-less hard cut whenever the marker itself would not fit in the remaining budget (a result is never bigger than the ceiling it was given, nor bigger than the value it replaces), and the 20 top-level `byRefValues` positions now share the same budget pre-check the recursive subscript walk already had (`AddByRefPosition`) — a position is OMITTED from `byRefValues` entirely once the shared budget is already exhausted, rather than materialized as a misleading placeholder. Pinned at the REAL deployed endpoint with the exact review repro shape, mutation-verified RED when either half of the fix is removed.

**The `byRefValues` character budget now charges subscript keys and OREF placeholders, not just leaf values (code review, cycle 2).** The budget above was decremented only by each leaf VALUE's length, so subscript KEYS and `<Object:...>` placeholders were emitted free — meaning the advertised 32768-character `byRefValues` budget did not actually bound `byRefValues`. Measured live: an `Output` array of 400 positions keyed by 900-character subscripts emitted **363,908 characters** with 32,368 of the budget still reported unspent and `byRefTruncated` still `false`; 400 OREF out-values emitted ~16,000 characters without touching the budget at all. A long-keyed `Output` array (file paths, URLs, composite keys) is an entirely idiomatic ObjectScript shape, so this was reachable by ordinary callers — the same unbounded-payload class as CR-5, one field over. Every emitted piece of content is now charged; the same 363,908-character case now emits 32,797 characters with `byRefTruncated: true`. The per-node JSON scaffolding (~25-30 characters per container node) is still not charged and is bounded instead by the 1000-node ceiling, which is now stated explicitly at every doc site rather than implied away.

**The byRef elision contract is now stated in full (code review, cycle 2).** The tool description and README previously described a false dichotomy — a value that no longer fits is "either cut short with an elision marker … or omitted entirely". There is a third case the code has always produced and the story's own gate leg (e-4) pins as correct: when the remaining budget is positive but smaller than the ~40-character marker, the value is cut to a **plain unmarked prefix**. Both surfaces now describe all three outcomes and state plainly that in the unmarked case `byRefTruncated` is the only signal — so the absence of a marker must not be read as proof a byRef value is complete.

**Non-ASCII request-body content — documented, not fixed (code-review finding CR-7, review-continuation pass).** Every custom `ExecuteMCPv2.REST.*` handler's shared request-body parser (`ExecuteMCPv2.Utils.ReadRequestBody`, 14 handler classes / 46 call sites across all five servers) reads non-ASCII JSON content as if it were Latin-1, silently corrupting it on the way in — `HTTP 200`, no error, no flag — most directly affecting `iris_global_set`'s `value` (data corruption **at rest**), plus `iris_execute_command`'s `command` and `iris_execute_classmethod`'s `args`. Pre-existing across every epic and untouched by this story's actual code changes (Rule #52 scope discipline); a proper fix requires investigating IRIS's CSP request-body character-set negotiation. Per the code review's explicit ship/no-ship call, this is now documented prominently rather than shipped silently: a new "Known Limitations" note in both the suite README and `@iris-mcp/dev`'s own README, referencing ledger item `34-6-CR-7`.

**Epic-gate hardening (AC 34.6.2/34.6.3, `34-4-R1`/`34-4-R3`, internal — not a published-package behavior change).** The `iris_execute_classmethod` epic-done gate's leg (d) previously asserted only that `%SYSTEM.Version.GetVersion()` returned a version-looking string — identical in every namespace, so a regression dropping the `namespace` parameter entirely would still pass. It now calls a target that echoes `$NAMESPACE` and asserts the value both equals the requested namespace and differs from the configured default (mutation-verified RED when `namespace` is dropped). Separately, the gate's fixture-availability probe previously collapsed any failure (credential fault, network error, licence issue) into the same "fixtures not deployed" verdict as a genuinely missing fixture; it now re-throws anything that is not a genuine "document not found" response. `IRIS_REQUIRE_LIVE=1` is now armed on `@iris-mcp/dev`'s own `prepublishOnly` npm/pnpm lifecycle hook, mechanically confirmed via `pnpm publish --dry-run` to abort packaging (before a tarball is ever produced) when IRIS is unreachable.

**Zero-result guard machine-detectability (AC 34.6.4, `34-5-R1`, recorded Project Lead decision).** `iris_execute_tests`' zero-result guard (added in the prior Epic 34 story) previously returned content-only JSON with no `isError`/`structuredContent`, so a structured consumer reading `structuredContent.total` regressed from `0` to `undefined`, and an agent branching on `isError` recorded the call as a success. It now carries **both** `isError: true` **and** `structuredContent` set to the same `{total, passed, failed, skipped, details, error}` object shown in the text content — both halves are required, not an either/or, since the guard fires only when the target produced nothing (a failed request, not a clean run). Applied identically to every guard path (package/class/method levels and the package discovery-time check) via one shared helper, so the paths cannot diverge again.

**Packaging gate extended to every IRIS-touching package (QA finding, internal — not a published-package behavior change).** `@iris-mcp/dev`'s own `prepublishOnly` gate only ever protected `@iris-mcp/dev` itself. `.changeset/config.json` groups every `@iris-mcp/*` package as `"fixed"`, so a real release always version-bumps and publishes `@iris-mcp/shared`, `@iris-mcp/admin`, `@iris-mcp/data`, `@iris-mcp/interop`, and `@iris-mcp/ops` (plus the `@iris-mcp/all` meta-package) alongside `@iris-mcp/dev` in the same event — none of which had any live-IRIS check of their own. Confirmed live (dry-run only) that `pnpm -r publish` processes packages in dependency-topological order: `@iris-mcp/shared` (a dependency of every other package) packaged and "published" completely BEFORE `@iris-mcp/dev`'s gate ever ran and correctly failed closed on a simulated credential fault — in a real release `@iris-mcp/shared` would already be on the registry by the time that failure is observed. A new shared script, `scripts/verify-iris-reachable.mjs`, is now wired as `prepublishOnly` on `@iris-mcp/shared`, `@iris-mcp/admin`, `@iris-mcp/data`, `@iris-mcp/interop`, `@iris-mcp/ops`, and `@iris-mcp/all` — a minimal, unconditional IRIS-reachability check (not a substitute for `@iris-mcp/dev`'s own deeper epic-done regression suite, which only makes sense for the package that ships that specific tool). Mutation-verified: the same bad-credential recursive dry-run that previously produced a complete `@iris-mcp/shared` tarball now produces zero tarballs before `@iris-mcp/dev`'s own gate is even reached; a good-credential run still publishes both packages cleanly. Wired into `@iris-mcp/client-config` as well. That package has no IRIS dependency of its own, and the first pass deliberately excluded it for that reason — but code review reversed the call: `.changeset/config.json` puts every `@iris-mcp/*` package in one `"fixed"` group, so they always publish as a single event, and `client-config` sorts FIRST in `pnpm -r publish`'s dependency-topological order. Left ungated it was the one package that could reach the registry before any gate in the release fired at all, confirmed live by a bad-credential dry run that produced a complete `client-config` tarball; re-verified after wiring that the same run now produces zero tarballs, while a good-credential run still publishes all eight packages cleanly.
