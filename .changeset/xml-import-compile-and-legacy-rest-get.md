fix(dev,data): XML import compile parity + legacy REST get routing (Epic 35, Story 35.6)

**`iris_doc_xml_export:import` compile parity (35-SWEEP-8).** Import previously loaded definitions WITHOUT compiling and reported bare success — the imported class then failed with `<CLASS DOES NOT EXIST>` until a separate `iris_doc_compile`. Additive `compile` (boolean, default false) and `flags` (string, only used when `compile` is true) parameters now mirror `iris_doc_load`: `compile: true` sends the native Atelier `flags` query param with the `c` compile qualifier folded in automatically when absent or explicitly negated (IRIS qualifiers are case-insensitive and `-c` negates — the fold guarantees an EFFECTIVE final `c`, so `-c` becomes `-cc`), so documents compile in the same call. When `compile` is omitted/false the request is byte-identical to the previous behavior (no `flags` param) and the response gains an honest note that the documents are NOT compiled, naming the remedy. Non-empty per-file `status` text from the load response (where IRIS reports compile errors while still answering HTTP 200) is now surfaced in the response text. Live-probed on IRIS 2026.1: `flags=ck`/`flags=c`/`flags=C` compile, `flags=k`/`flags=-c` and no flags do not; broken XML with `compile: true` surfaces `ERROR #5475` in the per-file status.

**`iris_rest_manage:get` legacy routing (35-SWEEP-9).** `list` with `scope:"legacy"`/`"all"` returns hand-written `%CSP.REST` apps (e.g. `/api/executemcp/v2`), but `get` on such a name previously 404'd via the IRIS Management API with the CSP gateway's misleading "Check the IRIS web server configuration" text — a by-design scope boundary (the Mgmnt API covers spec-first apps only), not a misconfiguration. `get` now branches on the HTTP 404 STATUS (never the message text) and falls back to the legacy webapp list: a legacy name resolves to `{name, dispatchClass, namespace, swaggerSpec: null, explanation}` (`fullSpec` deliberately has no effect — no spec exists), and a name in neither scope fails with an accurate not-found naming BOTH scopes checked. Spec-first `get` is unchanged. `delete` remains spec-first-only: a legacy name fails with an explanation pointing at `iris_webapp_manage:delete`, which is the correct tool for removing a legacy web application.
