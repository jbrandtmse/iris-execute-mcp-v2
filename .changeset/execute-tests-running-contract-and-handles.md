feat(execute): `iris_execute_tests` running-result contract, run handles, caller-controlled wait budget (Story 36.1)

`iris_execute_tests` no longer reports a genuinely-still-running slow suite as a timeout error. When the wait budget expires with the Atelier job still executing, the tool now returns `isError: false` with `structuredContent.status: "running"`, the run's `jobId` and (once populated) `runIndex`/`runIndexSource`, and a `partial` snapshot of whatever has drained so far (`partial.total`/etc — never a top-level `total` a consumer could mistake for a final count). The response text leads with an unmistakable "Do NOT re-submit" instruction — re-submitting the same target starts a SECOND concurrent run against shared test fixtures, which is exactly the failure mode the first beta report (OcuPilot, 2026-09-10) hit: a multi-minute suite exceeded the tool's hard-coded 120-second budget, surfaced as a bare `Error: Test execution timed out` with no job handle, and the caller's only move (re-submit) created concurrent runs against shared fixtures.

A completed run's envelope gains the same additive `status: "completed"`, `jobId`, `runIndex`, and `runIndexSource` (`"queue"` — captured from `IRIS.TempAtelierAsyncQueue(<jobId>,"unittest","id")` on a still-running poll via the pre-existing `iris_global_get` custom-REST route, no new ObjectScript — or `"counter"`, for a COMPLETED run only, when `^UnitTest.Result` read just before queueing vs. after completion moved by exactly 1 and the run drained result rows; otherwise `null` with a `runIndexNote` saying why) fields; existing `total`/`passed`/`failed`/`skipped`/`details` fields are byte-identical (Rule #19 — pinned by a `toEqual` minus-additive-fields test). A still-running result is never counter-attributed (its worker may not have allocated its index yet, so a delta of 1 could be another client's run). Every envelope — completed, running, the zero-result guard, "no job ID" and the polling-error catch — is built by ONE shared helper; a polling failure (HTTP error or network timeout) on an already-queued job returns its `jobId`, drained-so-far rows and the re-attach hint instead of losing the handle. The running `hint` carries the manual re-attach calls, live-run: the SQL joins `%UnitTest_Result.TestMethod` → `TestCase` → `TestSuite` → `TestInstance` (the only table with `InstanceIndex`) and selects `TestInstance.DateTime AS FinishedAt`, because those rows exist while the run still executes.

A new optional `timeout` parameter (positive seconds) overrides the tool's wait budget per call; an operator may also set a process-wide default via `IRIS_TEST_TIMEOUT` (seconds; precedence `timeout` argument > `IRIS_TEST_TIMEOUT` > the existing 120-second default). Both are hard-capped at 3600 seconds, with `timeoutCapped: true` in the response when clamped (mirroring the `IRIS_SQL_MAX_ROWS`/`rowsCapped` precedent). `@iris-mcp/shared`'s `IrisConnectionConfig` gains the additive, optional `testTimeoutMs` field feeding this — `undefined` when `IRIS_TEST_TIMEOUT` is unset, matching `sqlTimeoutMs`'s existing convention exactly — and `mergeProfile` inherits it into every named profile (like `sqlTimeoutMs`), so the knob is not inert on calls that target a named `server` profile.

Three narrow pre-existing defects in the same handler (ledger `34-5-R2`/`34-5-R3`/`34-5-R4`, carried since Story 34.5) were closed alongside this fix since they live in the exact code this story rewrites:
- A malformed `level: "method"` target (more than one `:` separator, or an empty class segment before `:`) now returns an explicit, distinct error instead of silently mis-parsing. The pre-existing missing-colon and trailing-colon parse edges are UNCHANGED.
- A test method named literally `Test` is now counted and its result restored correctly, both at class level and when targeted directly by name — previously a truthiness check on the (post-prefix-stripping, potentially empty-string) method name silently dropped it and could collide with the class-summary accumulator key. Verified live: BOTH the return leg and the Atelier request-leg filter (`methods: [""]`) work correctly once the return-leg truthiness bug is fixed — the Atelier endpoint's `methods` filter CAN target a method named exactly `Test`; the earlier "matches nothing" observation was itself a symptom of the return-leg bug, not a server-side limitation.
- At `level: "method"`, a drained result whose restored method name does not match what was requested (the Atelier endpoint's `Test`-prefix-stripped wire filter is many-to-one — `Class:Validate` and `Class:TestValidate` both resolve to the same filter) now carries an additive `methodMismatchWarning` field naming the mismatch, rather than silently reporting a normal-looking passing result for a target that does not exist under the name the caller typed.

`iris_doc_compile`'s `async` parameter description is also corrected: it promised "a job ID for polling" that the tool does not return (it returns `{mode: "async", docs, response}` immediately, with no poll companion route) — the description now states what is actually returned.

**Testability seam:** an injectable `now`/`sleep` clock pair (`TestClock`, exported alongside a `createExecuteTestsHandler(clock?)` factory) lets the running-branch and handle-capture logic be pinned without burning wall-clock time — the first such seam in this repo, chosen over `vi.useFakeTimers()` for its smaller footprint. `executeTestsTool.handler` is `createExecuteTestsHandler()` with no argument (the real clock), so production behavior is unaffected.

**Back-compat (Rule #19):** no new tool, action key, or governance key — `iris_execute_tests` keeps its existing bare (no-`action`) `write` classification, its default-ENABLED state (a grandfathered frozen-baseline member), and its frozen Epic-14 governance-baseline membership (`1e62c5ad5bf7`, 141 keys, unchanged). The three pre-existing accumulate-every-drain poll-loop regression tests pass with their test bodies and assertions byte-identical — only the describe-level mock plumbing now routes the new `/global` reads to their own mock — and are mutation-proven to still fail on both historical truncation shapes (first-drain-only, last-drain-only).
