fix(oauth,interop-rest): rework `iris_oauth_manage` client-create to the real 1-arg RegisterClient flow, add `sslConfiguration` to discover, and correct `iris_interop_rest`'s `name` contract (Story 35.5, ledger `35-SWEEP-6`/`35-SWEEP-7`)

**`iris_oauth_manage` client-create had never worked on IRIS 2026.1.** The handler called `%SYS.OAuth2.Registration.RegisterClient(tServerName, .tProps)` with two arguments, but that method takes ONE on this version (`RegisterClient(applicationName)`) — so every client-create died with a raw `<PARAMETER>` arity error before any validation could run. The branch now implements the real flow: `serverName` is resolved as the exact issuer URL of an existing `OAuth2.ServerDefinition` (created by a prior successful `discover`), a clean precondition error names both prerequisites when it is absent (run `discover` for the issuer first; discover of an https issuer itself requires an IRIS SSL/TLS client configuration — inspect with `iris_ssl_list`, create with `iris_ssl_manage`), the `OAuth2.Client` record is created (ClientType defaults to `confidential`, SSL configuration inherited from the server definition, redirect URI parsed into the `RedirectionEndpoint` serial), and registration goes through the real 1-arg `RegisterClient`. A failed remote registration (e.g. the issuer, like Google, publishes no dynamic registration endpoint) leaves the local client record saved — matching the Management Portal's configure-then-register semantics — and the error says so. Client secrets are still never returned (NFR6).

**`iris_oauth_manage` discover gains an additive `sslConfiguration` parameter (no new tool or action key).** The old call bound `Discover`'s second (by-value `sslConfiguration`) argument incorrectly against the 3-arg signature `Discover(issuerEndpoint, sslConfiguration, Output server)`, so every https discover failed with ERROR #6159 and even a successful discover returned an empty `configuration` object. `sslConfiguration` is now forwarded tool → handler → Discover, the discovered server is bound via the Output argument, and an omitted `sslConfiguration` on an `https` issuer is rejected before delegating with guidance naming the prerequisite and the tools that satisfy it. Discovery SAVES a server definition keyed by the exact issuer URL; that URL is the `serverName` a later client registration references — both README and tool descriptions now document the full precondition chain.

**`iris_oauth_manage` client-delete had never worked either (AC 35.5.6).** The delete branch called `##class(OAuth2.Client).Delete(name)`, a classmethod that does not exist on this version (`<METHOD DOES NOT EXIST>` on every call). It now pre-checks existence (`%ExistsId`, with a clean "No OAuth2 client named … exists" error) and calls `OAuth2.Client.DeleteId(name)` — the IdKey is the application name. Route-level coverage pins both legs (delete works; not-found is clean), mutation-verified RED on the wire.

**`iris_interop_rest`'s `name` description documented an example the implementation rejects.** The description showed `'/myapi'`, which `%REST.API.CreateApplication` rejects (`$ZNAME` package-name validation); the description now states the package-name contract with working examples (`'MyApi'`, `'MyCompany.MyApi'`) and names `'/myapi'` as the rejected form. The interop README create example was wrong on three counts (rejected name, plus an output shape the handler does not produce) and is corrected on all three.

**Back-compat:** client-create and https discover had no prior working behavior (both always errored), so nothing working changed; `sslConfiguration` is optional and absent from the wire when omitted (schema-pinned). Verified live against the deployed route AND the built tool layer over real HTTP: mutation-verified RED (old code redeployed → raw `<PARAMETER>` on the wire; discover with `sslConfiguration` supplied still failed) then GREEN (clean precondition errors; a real discover of `https://accounts.google.com` returning the full documented configuration). Permanent route-level coverage: `ExecuteMCPv2.Tests.OAuthClientValidationTest` (6 tests driving the deployed REST route). Governance baseline unchanged (`gen:governance-baseline:check` exit 0 at 141 frozen / 201 live / 60); tool and action counts unmoved (E-1).
