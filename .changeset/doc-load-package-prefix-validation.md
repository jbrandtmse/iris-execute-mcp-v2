fix(dev): iris_doc_load refuses path/content name mismatches; additive baseDir parameter (Epic 35, Story 35.9)

A trap-shaped glob whose only wildcard sits AFTER the package directory (e.g. `.../src/ClineTest/*.cls`) silently stripped the package prefix: the literal `ClineTest` segment was folded into the inferred base directory, so `ClineTest.Wumpus.cls` uploaded as unqualified `Wumpus.cls`. The upload reported success (`uploaded: 2, failed: 0`) — IRIS actually stores a mismatched PUT under the CONTENT-DECLARED name and reports the mismatch only as a string-typed `status` field the HTTP client never throws on — and the failure surfaced three steps later as a misleading compile error (`Class 'User.Wumpus' does not exist`). The tool now parses each `.cls`/`.mac`/`.int`/`.inc` file's own `Class <Pkg.Name>` / `ROUTINE <Name>` declaration and REFUSES the upload when it disagrees with the path-derived name, with an error naming BOTH names and both remedies (a wildcard before the package directory, or the new `baseDir` parameter); refused files are never uploaded and never reach the compile step. Headerless files (`.inc` fragments, CSP pages) keep pure path-derived naming. New optional `baseDir` parameter: when supplied it is used verbatim instead of glob-shape inference, so programmatic callers can state the package root deterministically; when omitted, name inference is byte-identical to before. `baseDir` does not bypass the cross-check — it is defense-in-depth, not an override. Two further silent-drop hardenings: a leading UTF-8 BOM is stripped from file content before upload (IRIS rejects a BOM'd first line as `ERROR #16021: Illegal Header Line` while storing nothing), and a per-document error the server reports only as a string-typed `status` field on an otherwise-HTTP-200 PUT response is surfaced as an upload failure in `failures[]` instead of being silently counted as uploaded.
