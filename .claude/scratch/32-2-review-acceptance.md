## Findings (most severe first)

### 1. MEDIUM — AC 32.2.3's "byte-for-byte" is not what the recorded check proves; epics.md not amended (skill Rule 5)
**Violates:** AC 32.2.3 as written (spec-conformance honesty; the epic's own amend-in-place discipline, applied to AC 31.0.3/31.6.1).
**Evidence:** `epics.md:4417` — "matching `iris_server_profiles` output for a running server **byte-for-byte** in a recorded check" stands unamended. The recorded check (story Debug Log): CLI `universe --json` renders **202** keys; the running `iris-dev-mcp` reported **151**; the PASS is **key-for-key agreement (value + configSource) over the 151 server-reported keys** — subset agreement, not byte-for-byte output equality (different key counts, different payload shapes). The story record itself is honest about the numbers, and the mechanism deviation (`universe` instead of the Task-3 text's `effective`) IS properly recorded (Completion Note 3, sprint-status entry) — the gap is that the AC text was never amended to the weaker, accurate claim, while this epic amended two other ACs for lesser deviations. The webview inherits the overclaim: `governanceView.ts` summary line — "Shown exactly as the governance engine computes it — the same render a running server's iris_server_profiles reports" — is per-key true only over each server's registered subset; any one server reports fewer keys than the 202 the pane shows. Remedy: amend AC 32.2.3 in epics.md in place (original wording + dated rationale) to "key-for-key over the server's registered key universe", and consider qualifying the webview summary line.

### 2. LOW — Case-sensitive `IRIS_` scrub in `buildGovernanceCliEnv` (the 32-3-R9 class, one story later)
**Violates:** Dev Notes constraint "Credential containment: … scrub IRIS_USERNAME/IRIS_PASSWORD/IRIS_PROFILES before spawning the CLI" and the module banner/README/CHANGELOG claim "scrubs EVERY `IRIS_*` variable".
**Evidence:** `extensions/iris-mcp-launcher/src/governanceEngine.ts:176` — `if (name.startsWith("IRIS_")) continue;`. On Windows (case-insensitive environment) an ambient `iris_password` / `iris_governance` survives into the spawned CLI's env. The CLI never reads credential vars, so there is no behavioral leak into the cascade render — but the containment claim is not literally true, and the suite fixed this exact class case-insensitively (`toUpperCase()` scrub) in 32.1's QA e2e and in this story's own `governanceUiRoundTrip.test.ts` child-env. `governanceEngine.test.ts`'s scrub tests exercise uppercase vars only.

### 3. LOW — No spawn timeout; a never-settling CLI child wedges the panel's `busy` guard permanently
**Violates:** AC 32.2.1/32.2.2 robustness intent (the AC 31.5.5 "one clear message, no wedged UI" bar).
**Evidence:** `governanceEngine.ts` `runGovernanceCli` has no timeout; `governancePanel.ts` sets `busy = true` around chooseFile/refresh/save/switchProfile and resets it only in `finally` after the awaited spawn settles. A hung child — the realistic case being a stalled `npx -y -p …` download on first post-publish run — leaves `busy === true` forever; `busy` lives in the `createGovernancePanelOpener` closure and survives panel dispose/reopen (`onDispose` clears `panel`/`state`, not `busy`), so every busy-guarded interaction is silently ignored until a window reload. Unreachable in npx mode today (packages unpublished); local CLI hangs are unlikely — hence LOW.

### 4. LOW — npx resolution mode spawns `npx` directly without a shell — dead on Windows post-publish
**Violates:** Task 1's recorded resolution contract (npx is the primary mode once `@iris-mcp/*` is published).
**Evidence:** `governanceEngine.ts:154-157` returns `{ command: "npx", … }` and `realSpawn` passes it to `node:child_process.spawn` with only `{ env }`. On Windows `npx` is a `.cmd` shim; `spawn` without `shell: true` cannot execute it (ENOENT/EINVAL since the Node CVE-2024-27980 hardening). The server-spawn path never hits this because VS Code spawns `McpStdioServerDefinition` itself. Latent today (docs correctly state npx mode cannot resolve pre-publication; `developmentRepoPath` is the only live path) and it fails gracefully (spawnError rendered inline), but it is the primary end-user mode after publication and it fails on the suite's own dev platform. Belongs with the 31-4-7 publish-gate decisions.
