# Story 33.2: `iris-mcp-clients` CLI

Status: done

## Story

As an iris-mcp user,
I want an `iris-mcp-clients` CLI that detects my MCP clients, shows the client × server matrix, and applies/enable/disables/removes iris-mcp server entries with diff-confirm and doctor diagnostics,
so that wiring the suite into any supported client is one command instead of a copy-paste-JSON ritual.

## Acceptance Criteria

1. **AC 33.2.1** — Full command surface over the engine: `detect`, `status` (`--json`), `apply --client <id> --servers <list> --scope user|project --mode <mode>` (diff + confirm; `--yes` skips), `enable|disable --client <id> --server <name>`, `remove`, `diff`, `doctor` (env-reference resolvability, file parseability, stale-backup and orphaned-stash detection, restart hints).
2. **AC 33.2.2** — Rule #22 dist smoke in a fresh Node process against a sandbox HOME: `apply` to fixture Claude Code + Codex + Goose configs (one per format family) → `status` shows enabled → `disable` → `enable` → `remove` → files byte-equal originals.
3. **AC 33.2.3** — Exit codes and `--json` stable for scripting; every write path prints the client's restart hint.
4. **AC 33.2.4** — Rule #51: any counts the CLI prints (clients detected, servers managed) are derived from the data structures, never hand-authored in copy.

## Integration ACs

**AC 33.2-I1** — This story IS the integration: the CLI is the first external consumer of the 33.0/33.1 engine. Every command drives the REAL engine functions (`detect`/`status`/`diff`/`apply`/`enable`/`disable`/`remove`/`restore`/`synthesizeEntry`) imported from the built dist — a mechanical source-scan pin asserts the CLI module contains no re-implemented parse/splice/serialize logic (no `jsonc-parser`/`smol-toml`/`yaml` imports in the CLI file; those live only in the engine). AC 33.2.2's lifecycle produces the observable file effects.

**AC 33.2-I2** — `doctor` closes deferred item **33-1-R5** (state.json loss orphans non-canonical manager-created entries): doctor DETECTS present-non-canonical-unrecorded entries and offers to re-record them manager-created behind a typed confirmation (the ledger row's suggested resolution, executed in this story as agreed at the 33.1 review).
