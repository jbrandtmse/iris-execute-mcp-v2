# Story 35.3: MEDIUM - Pin the Request Locale for Error Text

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an **operator of the IRIS MCP suite on an English-locale instance**,
I want **the HTTP client to pin the request locale explicitly**,
so that **`%Status` error text renders in a predictable language instead of whatever locale IRIS resolves from an unspecified `Accept-Language`**.

## Context — why this story exists

Ledger item `35-SWEEP-3` (MEDIUM). `Accept-Language` is never set anywhere in the suite ([http-client.ts:183](packages/shared/src/http-client.ts#L183) builds headers without it), and IRIS resolves the effective `*` to the alphabetically-first locale (`araw`), localizing every `%Status` error prefix — on an instance whose own locale is `enuw`.

**This fix addresses ONE of TWO independent mechanisms.** That distinction is the whole risk of this story, and AC 35.3.4 exists to protect it.

## Acceptance Criteria

1. **AC 35.3.1** — The shared HTTP client sends an explicit `Accept-Language` header (`packages/shared/src/http-client.ts`, header construction ~L183). Today none is sent, and IRIS resolves the effective `*` to the alphabetically-first locale (`araw`), localizing every `%Status` error prefix suite-wide.
2. **AC 35.3.2** — Oracle pinned from live behavior (#36), captured 2026-08-17 by curl against `POST /api/executemcp/v2/classmethod` with a nonexistent class: `Accept-Language: *` → `خطأ #5001: ...`; `Accept-Language: en-US,en;q=0.9` → `ERROR #5001: ...`; no header → `ERROR #5001: ...`. Instance locale is `enuw`.
3. **AC 35.3.3** — The value is operator-overridable (env var), defaulting to English. Hard-coding English with no escape hatch is wrong for non-English deployments.
4. **AC 35.3.4** — **All existing localized-prefix handling is PRESERVED.** This fix addresses ONE of TWO independent mechanisms. Verified still required: `ExecuteMCPv2.Utils.cls:181` strips both `"ERROR #"` and `"خطأ #"` (Rule #8), and `ExecuteMCPv2.Diagram.Loader.cls:168-214` normalizes locale words on resolved renderings because `GetErrorText` picks the message table PER WORKER PROCESS (Rule #13) — a mechanism the request header does not control, found by the 2026-07-03 SADEMO smoke. Removing either would re-open a previously fixed bug. The story must not claim to eliminate localized prefixes wholesale.
5. **AC 35.3.5** — `packages/shared/src/__tests__/http-client.test.ts:1084-1129` (the Arabic-prefix UTF-8 preservation test) still passes UNCHANGED. It asserts multi-byte text is not mangled using a MOCKED envelope; it is not a locale test and must not be weakened or deleted to accommodate this change (#54 — a fake must stay something the real API can return, and IRIS can still return Arabic under an operator override).
6. **AC 35.3.6** — Live proof across at least two servers that a real error now renders `ERROR #` on the MCP path, plus one call with the override set to a non-English locale showing the header is genuinely honored (proving the knob is not inert — Rule #59).

## Dev Notes

### The lead's own observation was NOT clean evidence — read this before designing the probe

During the Story 35.2 smoke the lead saw a `curl` with no `Accept-Language` return `ERROR #5001` (English) while the MCP tool returned `خطأ #5001` (Arabic), and initially read that as confirming the header mechanism. **That inference does not hold**: the two calls hit DIFFERENT endpoints and therefore potentially different CSP worker processes, and Rule #13 says `GetErrorText` picks the message table **per worker process**. The observation is equally consistent with the second, independent mechanism.

It is recorded here as a caution, not as evidence. **Your Task 1 probe must isolate the variable**: same endpoint, same error, vary ONLY the header — and check stability across repeats to detect worker-process drift. This project's own retro is explicit that "a written finding is a lead, not a fact"; that applies to the lead's findings too.

Note also that AC 35.3.2's captured oracle says **no header → `ERROR #`** (English), while AC 35.3.1 says the effective resolution of an unspecified `Accept-Language` is `*` → Arabic. Those two statements are in tension on their face. Resolving that tension empirically is the point of Task 1 — do not paper over it, and do not assume either is wrong until the probe says so.

### The two mechanisms, kept straight

| | Mechanism | Controlled by | Handled by |
|---|---|---|---|
| 1 | Request locale negotiation | the `Accept-Language` header | **this story** |
| 2 | Message table selected **per worker process** | NOT the header (Rule #13; 2026-07-03 SADEMO smoke) | the EXISTING strippers — leave them alone |

Verified still present by the lead: `Utils.cls:181` — `For tPrefix = "ERROR #", "خطأ #"`; `Loader.cls:168-214` — documents the word-code variants (`ERROR #ErrGeneral:` / `خطأ #ErrGeneral:`) that stack INSIDE the re-wrap when the domain's message table cannot be resolved.

**The story must not claim to eliminate localized prefixes wholesale**, in the code comments, the docs, or the commit message. It pins the request locale. Mechanism 2 remains, which is precisely why the strippers stay.

### Rule #54 — why the mocked Arabic test must survive intact

`http-client.test.ts:1084-1129` uses a MOCKED envelope to assert multi-byte text is not mangled. It is a UTF-8 preservation test, not a locale test. Arabic remains something the real API can genuinely return — under an operator override, or via mechanism 2 — so the fake stays valid. Weakening it to accommodate this change would delete real coverage and violate Rule #54's "can the real thing return this?" test in the wrong direction.
