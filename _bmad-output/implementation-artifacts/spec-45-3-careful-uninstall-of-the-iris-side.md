## Intent

**Problem:** `ExecuteMCPv2.Setup.Uninstall()` (`src/ExecuteMCPv2/Setup.cls:103`) deletes only the `/api/executemcp/v2` web application. The install also creates the `%ALL` namespace (when absent), the `ExecuteMCPv2` package mapping in it, `^UnitTestRoot`, and the classes, and nothing records which of these the install created, so an administrator cannot return an instance to how it was without risking shared pieces (issue #1 point 3, owner decision (3)).

**Approach:** The install records, per namespace, what each step created (a global that survives deleting the classes). `Uninstall()` becomes one documented terminal command that removes the web application, the mapping, the classes (shadowed copies included), then `%ALL` and `^UnitTestRoot` only when the record says the install created them and they are unchanged, then the record; it reports what it removed and what it left and why, and is idempotent.

## Boundaries & Constraints

**Always:**
- **The record** is the global `^ExecuteMCPv2.InstallRecord`, in each namespace where an install step ran (probe P3: the `%ALL` package mapping does not map it, and it survives `DeletePackage`). Nodes: `("format")=1`; `("deployed")=<marker>` (set by `Configure(pNamespace)` in `pNamespace`); `("all")="created"|"found"` and `("mapping")="created"|"found"`, `("mapping","database")=<db>` (set by `ConfigureMapping(pNamespace)` in `pNamespace`, through an extended reference); `("unitTestRoot")=<value>` (set by `EnsureUnitTestRoot()` in the current namespace, only when it set the global). Each node is written only after its step succeeded; `"created"` is never overwritten by `"found"` (a `"found"` is written only when the node is undefined). A record write sits in its own Try/Catch and never changes the method's return value.
- **Uninstall order:** (1) the web application; (2) the `%ALL` `ExecuteMCPv2` package mapping; (3) the classes: in every namespace of `Config.Namespaces:List` except `%ALL` (probe P8: switching to it raises `<NAMESPACE>`), after the mapping is gone, `$System.OBJ.DeletePackage("ExecuteMCPv2","-d")` where any `ExecuteMCPv2.*` class definition exists, unless that namespace holds `ExecuteMCPv2.InstallGuard` (IPM-owned: classes left, report names `zpm "uninstall iris-execute-mcp-v2"` in that namespace); (4) `%ALL`, only when some namespace's record says `("all")="created"`, step 2 succeeded, and `Config.MapPackages:List`, `Config.MapGlobals:List` and `Config.MapRoutines:List` for `%ALL` all return no row (probe P1: never the SQL projections); (5) `^UnitTestRoot` in each namespace whose record holds `("unitTestRoot")`, only when the current value equals it; (6) every record, only when no step failed (a failed step keeps the records so a re-run can finish).
- After step 3 the method calls no other `ExecuteMCPv2` class (they may be gone; probe P4 proves its own methods keep running). Every Config/Security call runs in `%SYS` with the save/restore pattern (AD-13); a namespace that cannot be switched to or read is a failed item with IRIS's text, never a silent skip.
- **Report:** `Uninstall(pVerbose As %Boolean = 1, Output pReport) As %Status`. `pReport` is a `%DynamicObject` `{removed:[], left:[], failed:[], namespaces:[]}`; each entry `{item, namespace?, detail|reason|error, manual?}`; `namespaces` lists every namespace with a `("deployed")` node or with `ExecuteMCPv2` classes found by the scan, and when it holds more than one the report prints the two-namespace line of the I/O Matrix. With `pVerbose`, one line per entry on the current device (`Removed: ...`, `Left: ... (reason). To remove it by hand: ...`, `Failed: ...: <IRIS text>`), then the always-printed line about a running server (I/O Matrix). Errors carry `$System.Status.GetErrorText(tSC)` (IRIS's real text, Rule #9; `Utils.SanitizeError` is not callable once the classes are deleted, and this is not a REST response). The returned status is `$$$OK` unless an item failed; then `$$$ERROR($$$GeneralError, "Uninstall did not finish: <failed item names>. See the report.")` (names only, so no prefix double-wraps, Rule #8).
- No record anywhere (an install by `1.2.0` or earlier, or one upgraded from it): `%ALL` and `^UnitTestRoot` are never removed; the report names `%ALL` (if it exists) with `Do ##class(Config.Namespaces).Delete("%ALL")` in `%SYS` and the warning that it deletes every mapping in `%ALL` (probe P5), and every namespace where `^UnitTestRoot` is defined with `Kill ^UnitTestRoot`.
- Back-compat (AD-15, Rule #19): `Configure`, `ConfigureMapping`, `IsConfigured`, `EnsureUnitTestRoot`, `GetBootstrapVersion` keep their `FormalSpec`, return type, `SqlProc` flag and return values; the install's visible effects are unchanged apart from the record. The bootstrap's requests are byte-identical (no TypeScript change to `bootstrap.ts`).
- The behavior change of `Uninstall` is `S-45.3-careful-uninstall` (AD-15), named in `CHANGELOG.md` and the changeset. `Setup.cls` changes, so `pnpm run gen:bootstrap` regenerates the embed and `BOOTSTRAP_VERSION` from → to is recorded (Rule #24).

**Never:**
- No new tool, action, governance key, preset change, CLI bin or REST route (the form is the documented one-liner, the lead's gate decision; see Design Notes). `Uninstall` is **not** `[ SqlProc ]`: an agent's `iris_sql_query` could otherwise call it in a SELECT (issue #1 point 2).
- Never run any uninstall, `%ALL` change or `^UnitTestRoot` change on the shared instance (`localhost:52773`); every live leg runs on a throwaway. `SetupTest` must not call the destructive `Uninstall()` at all (a test run on the shared instance would remove the suite).
- No new class (no roster change, Rule #39); no edit to generated files by hand, the IPM tree, frozen goldens, `irislib/`/`irissys/`. Never run `gen:ipm`, `pnpm run version` or the bare governance-baseline generator.
- Not in scope: DW-770; an IPM `Unconfigure` invoke (deferred above); removing `^IRIS.TempExecuteMCPv2Coverage` (IRISTEMP, written by coverage runs, cleared at restart; the README says so).
