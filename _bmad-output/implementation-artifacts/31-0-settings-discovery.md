# Story 31.0: Settings Discovery + Profile Mapping (shared)

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an **iris-mcp suite user who already manages IRIS connections in the InterSystems Server Manager VS Code extension**,
I want **the MCP servers to read my `intersystems.servers` definitions from VS Code settings files on disk**,
so that **I stop duplicating host/port/username into every MCP client's config — with today's behavior byte-for-byte unchanged until I opt in.**

## Acceptance Criteria

1. **AC 31.0.1** — `discoverSettingsFiles(env, platform)` returns candidate files in documented precedence order (workspace `.vscode/settings.json` from CWD or `IRIS_SM_WORKSPACE`, then user settings for Code, Code - Insiders, VSCodium, Cursor on win32/darwin/linux); `IRIS_SM_SETTINGS_PATHS` (path-delimited list) replaces discovery entirely; all paths derived from an injectable `env`/`platform` so every branch is unit-testable on any OS.
2. **AC 31.0.2** — `parseIntersystemsServers` uses `jsonc-parser`: comments and trailing commas parse; malformed JSONC in one file logs a warning and skips that FILE (never crashes startup in `auto`); `/default` and any `/`-prefixed keys skipped; `webServer.{scheme,host,port,pathPrefix}` + `username` map to the existing `ProfileOverride` shape with the same field validation as `IRIS_PROFILES` (via `mergeProfile`); `superServer` ignored; inline legacy `password` accepted with a deprecation warning naming the credentials CLI.
3. **AC 31.0.3** — `IRIS_SERVER_MANAGER` parsing fail-fast on unknown values naming the valid set; `off`/unset ⇒ the new module is never invoked; `required` ⇒ startup fails with an actionable error if zero definitions are **found** (counted before both the `IRIS_SM_SERVERS` filter and credential-completeness exclusion), and — with a distinct error naming `IRIS_SM_SERVERS` — if definitions were found but the allow-list matched none of them; `IRIS_SM_SERVERS` comma allow-list filters imported names (an unknown name WARNs, and fails only in `required` via that second error, never in `auto`). *(Amended during code review 2026-07-25 — see epics.md AC 31.0.3 for the full rationale: "resolve" → "found", per binding spec F1-D1, with credential-completeness escalation belonging to AC 31.1.1.)*
4. **AC 31.0.4** — Rule #19 mechanical back-compat proof in the default suite: with `IRIS_SERVER_MANAGER` unset, `loadProfileRegistry` output deep-equals its pre-feature output across the existing profile test matrix (fixtures include a populated `.vscode/settings.json` on disk to prove it is NOT read when off).
5. **AC 31.0.5** — Dev Notes document the Story 31.1 seam (Rule #52): this story ships profiles WITHOUT passwords marked `credentialStatus: "unresolved"`; 31.1 owns resolution. Unresolved profiles are excluded from the registry at this stage with a single startup log line.

### Integration ACs

**No consumers in this story.** `server-manager-source.ts` is a foundation module with no production consumer at this stage:
- **First consumer — Story 31.1** (credential chain): consumes `credentialStatus: "unresolved"` profiles and resolves passwords via env → keychain → helper → fail-with-remediation.
- **Second consumer — Story 31.3** (registry integration): owns the full `loadProfileRegistry` merge semantics — collision precedence with a log notice, `source: "env" | "server-manager"` provenance through the `iris_server_profiles` allow-list, and audit `profileSource`.

This story's own end-to-end exercise is AC 31.0.4's back-compat proof plus direct unit coverage of the three exported functions against on-disk fixture settings files. Per Rule #52 the seam is named explicitly in Dev Notes so 31.1/31.3 do not re-open this story's work.

## Dev Notes

**Scope seam — read this first (Rule #52).** This story owns the MODULE and its env parsing. It does NOT own: credential resolution (Story 31.1), or the full registry merge semantics — collision precedence notice, `source` provenance, allow-list surfacing, audit `profileSource` (Story 31.3). A minimal wire-in sufficient to make AC 31.0.4's proof meaningful and AC 31.0.5's exclusion real is in scope; rich merge semantics are not. **Lead's explicit scope call:** ACs 31.0.4/31.0.5 imply a minimal `loadProfileRegistry` touch while AC 31.3.1 assigns the full merge to 31.3 — build the minimal, provably-inert-when-off wire-in here and leave collision/provenance/audit to 31.3. Do not treat this as an ambiguity requiring a halt.

**The `mergeProfile` trap (highest-value guardrail).** `mergeProfile` (`packages/shared/src/profiles.ts:124`) and `ProfileOverride` (`:90`) are **module-private today** — AC 31.0.2 requires reusing that validation, so both must be exported. Critically, every validation failure inside `mergeProfile` routes through `profilesError()` (`:113`), which hard-codes the prefix `IRIS_PROFILES is invalid: `. Reusing it unmodified means a malformed *Server Manager* definition reports an error blaming a variable the user may not even have set. Parameterize the source label (e.g. an optional `sourceLabel` argument defaulting to `IRIS_PROFILES`) so Server-Manager mapping errors name the settings file and server instead. **Existing `IRIS_PROFILES` error text must stay byte-identical** — it is pinned by existing tests.

**pathPrefix — verified mechanism, and the trap.** `IrisConnectionConfig` has **no** `pathPrefix` field, but a prefix is still expressible: `IrisHttpClient` builds every request as `` `${this.config.baseUrl}${path}` `` (`http-client.ts:163`) and every `path` begins `/api/atelier/` (`atelier.ts:170`, `health.ts:31`). So a `baseUrl` of `http://host:port/prefix` yields exactly the right URL with zero changes to the client or Atelier layers. **The trap:** `mergeProfile` re-derives `baseUrl` via `deriveBaseUrl(host, port, https)` (`:101`, `:216`), which drops any prefix. If you map `pathPrefix`, apply it as a post-merge `baseUrl` override on Server-Manager-sourced profiles only — never by changing `deriveBaseUrl`, which would risk the Rule #19 back-compat gate for env profiles. Normalize the prefix (leading `/`, no trailing `/`) and unit-test the composed URL. An empty/absent `pathPrefix` must produce a `baseUrl` identical to today's derivation.

**Rule #19 shape discipline.** Follow the existing conditional-spread idiom used for `sqlMaxRows`/`sqlTimeoutMs` (`profiles.ts:223-224`): `...(x !== undefined ? { x } : {})`. New fields (`credentialStatus`, and later `source`) must not appear as `undefined` keys on env-sourced profiles, or AC 31.0.4's `toEqual` will fail. "Unset ⇒ field absent" is the contract.

**Secrets discipline.** Never log a password — not the legacy inline one, not in a validation error echoing a bad entry. Existing redaction (`iris_server_profiles` allow-list; audit key-pattern redaction) covers downstream surfaces, but this module's own warnings are new surfaces and must be secret-free by construction. Assert this in tests on captured log output.

**Rules that do NOT apply here** (stated so you don't go looking): no new MCP tool ⇒ Rule #28 (`mutates`) and Rule #53 (preset visibility disposition) are not triggered and **no tool count moves** (Rule #31). No ObjectScript/`.cls` ⇒ Rule #39 bootstrap rosters and `BOOTSTRAP_VERSION` are untouched. No new governance key ⇒ the frozen baseline `1e62c5ad5bf7` (141 keys) must remain unchanged; `pnpm gen:governance-baseline:check` must exit 0 (Rule #25 — run the `:check`, never the bare generator).

**Verified user-settings paths** (binding spec F1-D1) for products Code, `Code - Insiders`, VSCodium, Cursor:

- darwin: `~/Library/Application Support/<Product>/User/settings.json`
- linux: `~/.config/<Product>/User/settings.json`

**Why passwords are not readable here (do not attempt).** Server-Manager-saved passwords live in VS Code SecretStorage, encrypted via Electron `safeStorage` with an app-bound OS-keychain key; there is no supported CLI or IPC for an external process to read them. This is the load-bearing constraint behind the whole epic — the credential chain (31.1) exists precisely because this door is closed. Do not attempt SecretStorage/`state.vscdb` extraction.

- Security-conscious design decision (not explicitly spelled out in the story but required by AC 31.0.5's spirit): the "base" config `resolveServerManagerProfiles` merges each entry over is `{ ...loadConfig(env), password: "" }` — i.e. every OTHER field (namespace, timeout, sqlMaxRows/sqlTimeoutMs, username) inherits from the local default profile exactly like an `IRIS_PROFILES` entry does, but `password` is deliberately NEVER inherited. Without this, a Server-Manager profile with no password of its own would silently inherit the LOCAL default profile's password and be sent to a DIFFERENT host — a real credential-leak bug. A profile whose merged `password` is still `""` (no legacy inline password) is counted, logged once as a summary ("N server profile(s) skipped — no password available yet"), and excluded from the returned array (AC 31.0.5); Story 31.1 owns real credential resolution.
- `required` mode's fail-fast is based on ZERO TOTAL DEFINITIONS FOUND (before the password-completeness exclusion) — confirmed against F1-D1's "required (fail-fast if zero definitions found)" wording and the research spec's F1-D2 point 4, which separately describes a CREDENTIAL-completeness `required` escalation that explicitly belongs to Story 31.1. Verified live: `required` + a settings file containing one passwordless entry does NOT throw (one definition was found); `required` + zero files/entries DOES throw, naming the checked file paths.

Verified live and via test: `pathPrefix: "myprefix//"` → `baseUrl` ends `/myprefix`; an absent/empty `pathPrefix` produces a `baseUrl` byte-identical to today's derivation.
