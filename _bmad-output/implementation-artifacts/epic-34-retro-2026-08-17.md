## 2. What went well

- **Rule #57 earned its place on first use.** Epic 33 closed 6/6 reviews on silent layers; Epic 34 closed **9/9 with all three layers delivering**, never once degraded. Story 34.0 wired it in before any other work. Cleanest before/after in the project's history.
- **Probe-first beat reasoning twice, decisively.** Story 34.1's entire output was pinned live findings. In 34.8 the **ledger's own root-cause hypothesis was wrong** — `%request.GetMimeData("BODY")` is never populated at all; every call silently fell through to `%request.Content`. Reasoning would have produced a plausible fix for a non-existent mechanism.
- **The Project Lead's escalation calls were the epic's highest-value decisions.** Five re-opens, each surfacing defects every automated tier had passed: the empty-`200` outage, the ungated `client-config` publish, the surrogate on the wire, the 196,495-character understatement. Twice the Lead overrode an "it's documented, ship it" disposition — and both follow-up stories found real defects underneath.
- **Mutation verification became routine and repeatedly load-bearing.** Nearly every fix carries revert → red → restore evidence, and in at least three cases the mutation is the *only* reason the defect was found rather than shipped.
- **Adversarial layering worked as designed.** Dev caught its own catastrophic near-miss; QA caught the dev's; review caught QA's. Each layer found something the previous one missed, on the same code.

## 3. Challenges and patterns

### 3.1 The epic's defining pattern: gates that did not gate — codified as Rule #59

Six distinct instances, every one a green badge over a dead check:

| # | Instance | How it was caught |
|---|---|---|
| 1 | Epic gate was a disposable script; integration tests excluded from the default suite — capture broken live, suite stayed **614/614 green** | QA (34.3) |
| 2 | Epic-gate availability probe wrong in **both** directions: broken endpoint → "3 skipped, exit 0"; missing fixtures → hard-fail for an environment reason | Review (34.6) |
| 3 | Gate leg (d) **could not fail** for the property it claimed — `%SYSTEM.Version.GetVersion()` is namespace-invariant | Review (34.6) |
| 4 | The output ceiling had **zero coverage at its integration point** — both `ApplyOutputCeiling` calls deleted, live endpoint returned 50,000 untruncated chars, **643/643 green** | Review (34.6) |
| 5 | The surrogate pin round-tripped **inside IRIS**, which accepts its own WTF-8 — structurally blind to invalid UTF-8 on the wire | Review (34.7) |
| 6 | Publish gate armed `IRIS_REQUIRE_LIVE` for only the epic gate, so 34.8's sole end-to-end proof would have silently skipped and shipped the fix unexecuted | Review (34.8) |

Plus a seventh of the same family: the large-body test could not detect the truncation it existed to prevent — a regressed decode satisfied all three of its assertions while losing 801,596 characters.

**Disposition: codified as Rule #59** — a gate must be proven RED by breaking what it protects, *on the path it actually guards*, with that path named.

### 3.2 Defects clustered in the verification apparatus, not the product

The handler — the epic's actual deliverable — came through review with no HIGHs of its own. Nearly every HIGH was in a test, a gate, a probe, or a doc claim. Two fixes *introduced* new defects of the same class they were fixing (the byRef budget replacing small values with a larger marker; `$ZCONVERT` producing an unpaired surrogate that reached the wire as invalid UTF-8).

**Disposition:** this is the direct evidence behind Rule #59. No separate rule.

### 3.3 Documented numbers were wrong three times in a row

The response-size worst case was published as 98,410, corrected by QA to 106,405, then corrected by review to **196,495** (6× raw, 3.93× past the threshold that justified the ceiling) — wrong at six doc sites including **both MCP tool descriptions**, which are the immutable wire contract. Every escaping-neutral fixture was blind to it by construction.

**Disposition:** covered by existing Rules #51 (mechanical tallies) and #58 (fixture diversity). Application failure, not a rule gap.

### 3.4 Original scope was too narrow for what the bug implied

34.1–34.3 addressed the reported symptom. The five escalations addressed what the fix *touched*: response-path integrity, gate durability, tool-layer reachability, payload bounding, and request-path encoding. Each re-open was evidence-driven and correct — but the pattern suggests the initial scoping under-read the blast radius of a change to a shared REST handler.

**Disposition (Project Lead):** no rule. Re-opening on evidence is working as intended; the alternative is a speculative mega-epic.

## 8. Key takeaways

1. **A gate that has never been broken has never been tested.** Six times this epic, something that looked like protection was decoration. Rule #59 makes "prove it red, on the right path" the standard.
2. **Rule #57 paid for itself in one epic.** 6/6 silent → 9/9 delivered. Timing as a control, not a hope.
3. **The ledger's own hypotheses need probing too.** 34.8's documented root cause was wrong. A written finding is a lead, not a fact.
4. **Escalating on evidence beats scoping on prediction.** Five re-opens, five real defect clusters, zero speculative work. The alternative — guessing the blast radius up front — would have been slower and wronger.
5. **Fixes in a shared surface deserve the blast-radius treatment by default.** Two of this epic's near-misses would have broken every REST route at once; both were caught only by driving live HTTP across multiple handlers.
