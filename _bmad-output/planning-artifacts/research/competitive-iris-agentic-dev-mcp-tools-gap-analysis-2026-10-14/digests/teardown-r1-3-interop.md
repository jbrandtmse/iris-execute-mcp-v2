**Mechanism legend.**
- **GEN** = `IrisConnection::execute_via_generator`. It PUTs a transient class `IrisDevTmp.IrisDevRun<12-hex>` through Atelier `PUT /doc`, compiles it with `POST /action/compile?flags=cuk`, runs it through `POST /action/query` (`SELECT <cls>_Execute() AS result`), reads back the captured `Write` output, then deletes the scratch class through a `ScratchGuard`. It retries 3 times (100/200/400 ms) on network errors or HTTP 5xx (conn:522-700). **No permanent server-side code is installed.** Every ObjectScript snippet below runs this way.
- **SQL** = direct Atelier `POST /action/query`.

**Gate legend.** Enforcement is centralized "once, in `ServerHandler::call_tool`" (wg module doc, lines 1-22), driven by the `CLASSIFICATION` table (wg:425-660).
- **RO** = always allowed.
- **W** = the write gate. With no explicit setting, it is OFF on `SystemMode::Live` and ON on Development/Test. On Unknown it is OFF when the namespace looks like production. `IRIS_ALLOW_PROD` forces it ON (wg:236-250).
- **D** = the destructive tier. It is OFF until declared and is a subset of W (wg:252-271).
- **PG** = the per-server connection-policy `dispatch_gate`, with steps [0] code-edit block, [1] env template, [2] bulk-PHI, [3] global blocklist and [4] PHI-name (gate:52-171).

## Leads worth chasing
1. **Code injection under a read-only tier.** `hl7_schema_inspect` interpolates `schema`/`segment` unescaped into `"..."` ObjectScript literals inside a compiled scratch class (admin:2029-2046). The tool is classified `ro` (wg:442) and is not in the PG [0] code-edit set (that set keys on a `code` param). A crafted `schema` value would likely execute arbitrary ObjectScript with the write gate off. Similar raw interpolation exists in `iris_production start` (`production_name`, interop:213-219), which is at least Write-tier. Confidence: high on the interpolation, medium on exploitability (it was not executed).
2. **Business rules may be largely invisible.** The tool reads only `Ens.Rule.RuleSet` / `Ens_Rule.RuleSet`. Unverified belief from training data: modern IRIS rules are classes extending `Ens.Rule.Definition` with `XData RuleDefinition`, and `Ens.Rule.RuleSet` is legacy storage. If so, `list` returns few or no rules on current IRIS. The code comment cites the competitor's own research.md ("EnsLib.Rules.Definition does not exist"). Worth a live probe.
3. **Boolean typing bugs in diff and diagram.** `iris_production_diff` reads `Enabled` with `as_bool()` (interop:2318) and `mermaid_production` with `as_str()` (admin:2208). If Atelier `/action/query` returns %Boolean as JSON numbers (unverified), every enabled item is reported `modified` by diff and the disabled styling never renders in the diagram.
4. **Non-idempotent writes are retried.** The GEN retries up to 3 times on 5xx or timeout (conn:533-597). A credential create, lookup set, or production start whose response is lost after execution would run again.
5. **`body_where` is an unvalidated SQL fragment.** It is inside a SELECT, but subqueries could read arbitrary tables through a read-only tool (interop:766-773).
6. **The HL7 class-query names are unverified.** `StoredSchemaNames`, `SegmentStructureElements` and `MessageStructures` and their columns (`Name`, `FieldName`, `Description`, `StructureName`) were not proven to exist. The e2e test accepts "success OR any error_code" and is `#[ignore]` (tests/integration/test_admin_e2e.rs:436-480), so it would pass even if the queries were wrong.
