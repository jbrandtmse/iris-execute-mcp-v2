## Leads worth chasing
1. **Defective iris_generate_class:** it generates text but never uploads it. It compiles by name only through docker exec, ignores `server` and always reports `success:true`. This is a legacy LLM tool that still ships in all three tiers next to the agent-side `iris_generate`. It suggests the competitor's "generation" surface is mostly prompt-scaffolding (mod.rs:5832-5918).
2. **Truncation retrieval in the default tier:** in Baseline (the default), truncated compile and search results point to a log store whose reader, `iris_get_log`, appears to be Merged-only. Verify `log_store::apply_truncation`'s message and whether any Baseline tool can read a `log_id`. If none can, the truncated data is unrecoverable except by re-calling with `inline:true`.
3. **Cache key without server:** resolve_dynamic_dispatch and extract_message_map_routing can serve another server's cached answer within 60 s when `server` differs. Also check whether iris_doc's elicitation resume (mode defaults to "get") is classified ReadOnly by the central gate, so a resumed write would pass with the write gate off.
- Secondary: iris_doc_search slices `text[..600]` by byte. On a multi-byte UTF-8 boundary, such as the em-dashes common in docs, a Rust `str` slice panics (doc_search.rs parse_hits). Not exercised here; confidence medium.
- Secondary: SCM credential interpolation into scratch-class source (`IrisDevTmp.*`). Check whether the scratch class is deleted on every path, including failures, and whether SCM hooks or journaling capture it.
- Secondary: UserAction code 7 (text prompt) is elicited, but `after_user_action_code` takes `{answer_int}`. The user's text may never reach AfterUserAction (scm.rs:660-675, not fully read).
