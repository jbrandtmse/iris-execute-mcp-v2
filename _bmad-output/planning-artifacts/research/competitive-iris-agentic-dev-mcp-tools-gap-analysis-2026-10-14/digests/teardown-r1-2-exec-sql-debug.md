**Shared mechanisms (they apply to many rows):**
- **"Generator exec"** = `IrisConnection::execute_via_generator` (`iris/connection.rs:522`). It PUTs a scratch class `IrisDevTmp.IrisDevRun<uuid>.cls` via `/api/atelier/v{N}/{ns}/doc/...` (connection.rs:615,633), compiles it with `/action/compile?flags=cuk` (connection.rs:650), then runs it as `SELECT IrisDevTmp.IrisDevRun<id>_Execute() AS result` via `/action/query` (connection.rs:689). Last, a ScratchGuard deletes the class. The class is a plain `ClassMethod Execute() As %String [ SqlProc ]`. It redirects `$IO` to a `%Library.File.TempFilename` file, wraps user code in Try/Catch, snapshots `$ZERROR`, detects a device that was left switched, and reads the file back through `%Stream.FileCharacter` (connection.rs:732-770). On network errors or HTTP 5xx it retries 3 times with 100/200/400 ms backoff (connection.rs:521). No server-side code has to be pre-installed, but every call writes, compiles and deletes a class. Most tools below run through this.
- **Gate model:** `write_gate.rs` `CLASSIFICATION` (write_gate.rs:425) is enforced once in `call_tool`, with three tiers (ro / write / destructive) and per-action overrides. The write gate resolves in this order: operator env, then config file, then legacy allow_prod, then inference. Inference sets SystemMode Live to off and Dev/Test to on; when the mode is Unknown it is off for production-looking namespace names. The destructive gate is off unless declared, and it is forced off when writes are off (write_gate.rs:228-283).
- **`arbitrary_exec_gate`** (mod.rs:3424) is used by iris_execute and iris_ws_exec. It runs the Server-Manager policy `dispatch_gate` plus `policy_gate` with an audit entry, then a role gate (a "subject"-role instance requires `confirmed=true`), then a literal-only `Kill ^global` regex check that requires the destructive tier. Its own error text admits that indirect kills (`Kill @x`, Xecute, `##class`, `&sql`) are not detected.
- **Service-account routing:** `get_iris_for_exec_with_client` routes execution through a restricted IRIS identity (`IRIS_SERVICE_USERNAME`) with its own cookie jar. It is used by iris_execute, iris_query mode=write, iris_execute_method and iris_global set/kill (mod.rs:4434-4445, 4938-4948, 6952-6962, 6846-6865).
- **Every tool declares an MCP `output_schema`.** Read-only tools carry `read_only_hint`, and global_kill carries `destructive_hint`.

## Leads worth chasing
1. **Persistent WebSocket terminal (iris_ws_open/exec/close).** This is a stateful, variable-preserving ObjectScript session over the Atelier v7 `/terminal` endpoint, with no server-side install. Worth checking: interactive `READ` handling, multi-line `{}` blocks sent line by line, session lifetime (no idle TTL or max-sessions constant was found), and behavior behind a web-gateway prefix.
2. **SQL power modes in iris_query.** `explain` (plan_text + query_hash), `count` (no row transfer), and `write` with a `max_rows_affected` COUNT(*) pre-check and %ROWCOUNT. Also the read-mode keyword blocklist plus a role gate. The weak points are no row cap in read mode and the silent `rows_check_skipped`.
3. **Their debug and logs surface is much shallower than its tool names suggest.** iris_debug error_logs is a stub, map_int truncates dotted routine names, capture reads the scratch process's own $ZERROR, and debug_* likely query a non-existent SQL table. In Baseline/Nostub, iris_get_log is missing, which strands the log_ids that iris_test produces. Their test runner hard-codes `errors=0` and has no single-method targeting, and its "load from disk" path is non-functional. Also of interest: the client-held `%ctx` session token for iris_execute, the two-step global_preview→global_kill confirm token, and service-account routing for exec tools.

## Looked for, could not find
- A single-test-method parameter or async/polling execution in iris_test. TestParams has no such field and the run is synchronous with a timeout.
- Row cap, truncation or pagination in iris_query read mode.
- Idle TTL, max-session count or reaper for WS sessions (grep for idle, TTL and max_sessions in ws_session.rs found nothing).
- Range queries (`$Order` from/to), `$Data` metadata, numeric or arbitrary-character subscripts, and non-string values in iris_global.
- A Cobertura XML write path in the iris_coverage run branch.
- A `server` param on the 4 Baseline debug_* tools, and a `namespace` param on global_preview/global_kill.
- A size cap or chunked/offset reading in stream_inspect, and support for file streams, compressed streams or full `$lb` OIDs.
- Validation of the global name in global_kill before it is interpolated into `Kill ^<name>`.
