# Bug report — the MCP server exits at startup when the `default` IRIS profile is unreachable, even when every other registered profile is up

**Component:** IRIS MCP Server Suite — all five servers (framework path `McpServerBase.start()` in `@iris-mcp/shared`), multi-server profiles (Epic 14)
**Reported:** 2026-09-16 — verbal beta feedback, relayed by the Project Lead
**Severity:** Medium — availability only, no data loss, an env-var workaround exists — but it defeats the multi-server feature's core promise ("one process, several instances"): the moment one instance is down is exactly when an operator wants the others.
**Status:** CONFIRMED by source reading and by an empirical run against a closed local port (the shared IRIS instance was not touched). Analysis + fix plan by Mary (analyst), 2026-09-16. Implementation routed to `/bmad-correct-course`.

## Environment (for the empirical proof)

| | |
| --- | --- |
| Repo | `main` @ `2ed83ff` (post-Epic-36) |
| Built dist | `packages/iris-dev-mcp/dist/index.js`, `packages/shared/dist/index.js` (2026-09-11 06:07 build) |
| Host | macOS (Darwin 25.6.0), Node |
| IRIS | **none involved** — the `default` profile was pointed at `127.0.0.1:9` (a closed port). Nothing was started, stopped or written. |

## Summary

When the reserved `default` profile (synthesized from `IRIS_HOST` / `IRIS_PORT` / `IRIS_USERNAME` / `IRIS_PASSWORD`) fails its startup health check, `McpServerBase.start()` calls `process.exit(1)` **before the MCP transport is connected**. Profiles registered through `IRIS_PROFILES` or Server Manager are established lazily on their first tool call and are never consulted at startup, so a healthy secondary cannot keep the process alive. The MCP client sees a server process that exited with code 1 — "the server fails to start".

Desired behavior (Project Lead, 2026-09-16): the server starts and serves calls against every reachable profile; calls against the unreachable `default` return a connection error and succeed once it comes back, without a restart.

## Observed behavior

1. **Empirical run.** Built `iris-dev-mcp` dist, `default` → closed port, plus a second profile:

   ```
   IRIS_HOST=127.0.0.1 IRIS_PORT=9 IRIS_USERNAME=probe IRIS_PASSWORD=probe \
   IRIS_PROFILES='{"other":{"host":"127.0.0.1","port":52773}}' \
   node packages/iris-dev-mcp/dist/index.js </dev/null
   ```

   Result — exit code **1**; stderr:

   ```
   [INFO] Tool visibility: preset="full" visible=30 hidden=0
   [ERROR] IRIS health check failed: Failed to connect to IRIS at 127.0.0.1:9. Verify the host and port are correct, and that IRIS is running.
   ```

   No `Connected via stdio transport` line. The `other` profile was never probed (nothing listens on its port either; a probe would have logged a second connection error).

2. The `Fatal:` catch in each server's entry point (`packages/iris-dev-mcp/src/index.ts:31-34`) is never reached — the exit happens inside `start()` itself.

3. The path is framework-level (`server-base.ts`), so all five servers behave identically.

4. Single-server installs are affected in a second way: because the failure is fatal, an IRIS restart requires an MCP-server restart. There is no recovery path.

## Root cause

`packages/shared/src/server-base.ts`, `start()`:

- `:2023` — eagerly creates the `default` profile's client.
- `:2026-2034` — `await checkHealth(defaultClient)`; on rejection logs `IRIS health check failed: …` and calls **`process.exit(1)`**. The comment reads: "A failure here is fatal at startup, exactly as before — the default profile must be reachable."
- `:2090` — the transport connect (step 5) is only reached after steps 3–4.5, so the process dies before it can accept a single MCP request.

`checkHealth` (`packages/shared/src/health.ts:29`) is a `HEAD /api/atelier/` with a 5 s timeout that throws `IrisConnectionError` on any failure.

**Contrast — the lazy path already has the desired semantics for every non-default profile.** `getOrCreateClient` (`:2166`) → `establishProfile` (`:2220`) health-checks and negotiates on first touch; on failure it `drop()`s the client (`packages/shared/src/profiles.ts:708`) so the next call retries cleanly (AC 14.2.8), and `handleToolCall` (`:1528`) converts the throw into the structured result `Could not connect to server profile "<name>": …` with `isError: true`. The JSDoc states the asymmetry outright: "only the default profile's startup failure is fatal" (`:2141`).

### Why it was built this way (provenance)

- Epic 14 architecture decision D1 (`_bmad-output/planning-artifacts/architecture.md:396`): "The **default** profile's client is created eagerly at startup, preserving today's bootstrap/health-check/negotiation exactly."
- Story 14.1 Dev Notes (`_bmad-output/implementation-artifacts/14-1-multi-server-profiles-config-and-resolution.md:134`): "Non-default health-check failure throws … rather than `process.exit` — only the default profile's startup failure stays fatal."
- Introduced in commit `213756b` (Story 14.1).

The fatal exit is a **carried-over single-server behavior**. Before Epic 14 there was exactly one instance, so "IRIS is down" and "there is nothing to serve" were the same condition. Nothing in the PRD or architecture argues that a multi-profile process *should* die with its anchor; the failure path was simply never re-examined when profiles were added. Rule #19 ("off = today's behavior") correctly protected the success path — and silently froze the failure path with it.

## Blast radius of the current behavior

- **Multi-server:** any outage, maintenance window or network partition of the `default` instance makes all five servers unusable for every other instance. Today's only workaround is to re-point `IRIS_HOST`/`IRIS_PORT`/credentials at a healthy instance (making *it* `default`) and restart the client — reconfiguring to route around the failure.
- **Single-server:** no recovery without a restart.
- **Not affected in itself:** `iris_server_profiles` never connects (README `:472`) — but it is unreachable too, because the process is gone. The `iris-mcp-credentials test --connect` CLI reuses `checkHealth` and correctly throws; that is a diagnostic and stays as-is.
- **Ledger:** no `deferred-work.md` item covers default-profile reachability. The nearest — "[14.1 / MED] Non-default first-touch health-check failure caches the client but records no meta" — was resolved by AC 14.2.8 and concerns non-default profiles only. The Epic 36 retro does not mention this report.

## Fix options

### A — Eager attempt, non-fatal, lazy retry (RECOMMENDED)

Keep steps 2–4.5 exactly as today when `default` is reachable (success path byte-for-byte — Rule #19). On health-check rejection:

1. log at ERROR with the existing message, plus one line stating the new semantics ("continuing startup; tools targeting the default profile will return a connection error until it is reachable, then recover automatically");
2. `this.clients.drop(DEFAULT_PROFILE_NAME)` (AC 14.2.8 symmetry — no un-established client lingers);
3. leave `profileMeta` **unset** for `default` and skip negotiation + bootstrap;
4. proceed to connect the transport.

The first tool call on `default` then flows through the existing `establishProfile` path (health check → version negotiation → one-time bootstrap when `needsCustomRest`), identical to a non-default profile: retryable, in-flight-coalesced, structured error. The `process.exit(1)` is removed **for this case only**.

- **Code:** ~15 lines in `start()`; comment/JSDoc updates at `server-base.ts:1506-1510`, `:1924-1935`, `:2137-2141`, `:2220-2230` and the `ProfileClientRegistry` header (`profiles.ts:655-665`). No new files, no `BOOTSTRAP_VERSION` bump (pure TypeScript), no tool/action keys (Rule #31), no schema change.
- **Tests:** exactly one existing test flips — `packages/shared/src/__tests__/server-base.test.ts:558` "should call process.exit when health check fails" becomes "continues startup, logs, does not exit". All 38 test files that use a `stageDefaultStartup` helper stage the *success* path, which is unchanged, so they stay untouched.
- **`this.atelierVersion`** (private field, `:381`) is used only for the startup log and the eager bootstrap; `profileMeta` is the source of truth for calls. Optionally sync it in `establishProfile` when `profile.name === DEFAULT_PROFILE_NAME`; not required for correctness.

### B — Fully lazy `default` (no startup I/O)

Delete steps 2–4.5 outright. Simplest code, but: the one-time bootstrap (deploys and compiles the ExecuteMCPv2 classes — seconds to tens of seconds) moves **inside the first tool call**, risking the client's per-call timeout; the startup-time bootstrap report is lost; and it re-sequences fetch mocks for all 38 `stageDefaultStartup` files plus every "no extra fetches after start" assertion (`server-base.test.ts:728`, `server-param.test.ts:340`, `server-param-integration.test.ts:357`, `governance-enforcement.test.ts:285`, …). Larger blast radius for the same user-visible outcome. Not recommended.

### C — Non-fatal only when two or more profiles are registered

Preserves the literal single-server fail-fast, but forks semantics on registry size, keeps the no-recovery-without-restart behavior for single-server users, and adds a branch whose only purpose is to preserve a failure mode. Not recommended; listed as the zero-single-server-change fallback if the lead wants it.

### D — Strictness knob (`IRIS_REQUIRE_DEFAULT=true`) restoring fail-fast

Precedent exists (`IRIS_SERVER_MANAGER=required`). Not recommended now: speculative, and every env var costs rows in the README plus three client-config guides. Record as a deferred item with a named trigger (a beta user asks for fail-fast).

## Proposed story (for correct-course to slot)

**Title:** Default-profile outage must not take down the server — degrade and retry (`@iris-mcp/shared`, framework).
**Placement:** first feature story of the next beta-feedback epic (Epic 37), following the Epic 36 precedent (the `.0` slot reserved for the retro-review gate).

**Acceptance criteria:**

- **AC-1 (startup survives).** `default` unreachable + at least one other profile → `start()` resolves, `process.exit` is NOT called, the transport is connected; the ERROR log names host:port, the reason, and the continuation semantics.
- **AC-2 (others serve).** `tools/call` with `server: "other"` (reachable) succeeds while `default` is down.
- **AC-3 (default degrades, then recovers without restart).** A call on `default` while down → the existing envelope `Could not connect to server profile "default": …` with `isError: true` (no crash, no exit). Once reachable, the next call establishes (health → negotiation → one-time bootstrap when `needsCustomRest`) and succeeds. The client was `drop()`ed after the failed eager attempt; bootstrap is attempted exactly once across the recovery.
- **AC-4 (success path unchanged — Rule #19 mechanical proof).** With `default` reachable, the startup fetch sequence and `profileMeta` seeding are byte-identical; the existing eager tests (`server-base.test.ts:728` and peers) pass unmodified; `git diff --stat packages/*/src/__tests__` lists only the intentionally changed test file(s).
- **AC-5 (single-server).** Same semantics with only `default` registered (per L-2).
- **AC-6 (config errors stay fatal).** The other `process.exit(1)` paths in `start()` — audit-log directory not writable, malformed `IRIS_GOVERNANCE*`, `IRIS_PROFILES`, preset — are untouched. Invalid config ⇒ fail fast; unreachable peer ⇒ degrade.
- **AC-7 (gate proven red — Rule #59).** The AC-1/AC-3 tests live in the DEFAULT suite and are shown red with the fix reverted (mutation: reinstate `process.exit(1)`).
- **AC-8 (live smoke — Rules #22/#26/#48; no shared-instance changes).** Built dist, `default` → `127.0.0.1:9`, `other` → the real instance; over stdio JSON-RPC: `initialize`; `tools/call iris_server_info {server:"other"}` → result; `tools/call iris_server_info {}` → the `isError` envelope. Read-only traffic only (HEAD/GET).
- **AC-9 (docs).** README — Backward Compatibility (new bullet) and Profiles section (one paragraph on per-profile independence at startup); `docs/client-config/README.md` (startup-failure section near `:30`, `claude mcp list` note near `:289`); `CHANGELOG.md` "Pre-release — <date>" entry under Fixed; the JSDoc/comment sites listed under option A. `tool_support.md`: no tool/action key moves — no row change.

## Not in scope

- **Existence** of the `default` profile. `IRIS_USERNAME`/`IRIS_PASSWORD` remain required at startup (README `:109`, `packages/shared/src/config.ts:135-141`). This bug is about *reachability*, not configuration.
- Periodic re-ping / background monitoring. `health.ts` `ping()` is unused by `server-base` today; retry-on-call is sufficient.
- Per-profile reachability in discovery output (L-4).

## Workaround until fixed

Point the `IRIS_*` variables at a healthy instance (it becomes `default`), define the down instance under `IRIS_PROFILES` instead, and restart the MCP client. The server then starts; calls to the down profile return a structured connection error and recover on their own once it is back.
