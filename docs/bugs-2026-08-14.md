# Bug report: `iris_execute_classmethod` (iris-dev-mcp) fails on methods that `Write` to the current device

**Component:** `iris-dev-mcp` MCP server, tool `iris_execute_classmethod` (endpoint
`POST /api/executemcp/v2/classmethod`). Also reproduced against the same server's test-runner path
(`%UnitTest.Manager.RunTest`, invoked via a wrapper classmethod), suggesting this is a property of the
classmethod-execution transport itself, not specific to any one target method.

**Reported by:** live debugging session, 2026-08-14, working against a local dev IRIS container.

## What happens

Calling `iris_execute_classmethod` against any ObjectScript classmethod whose execution path emits
output via `Write`/`W` to the current I/O device — as opposed to a method that only computes and
`Quit`s a return value — fails with:

```
Error executing class method '<Class>.<Method>': IRIS returned a non-JSON response for
POST /api/executemcp/v2/classmethod. Expected an Atelier envelope but could not parse the body.
```

No ObjectScript-level error is reported — the failure is purely at the tool's response-parsing layer.
This is a distinct failure mode from an actual runtime error in the target method (which the tool
reports cleanly, e.g. `{"returnValue":"Status: <error text>...`, when the method itself is
capture-wrapped — see Workaround below).

## When it occurs — confirmed reproductions

Three unrelated target methods across two different tool calls, all sharing the same property (direct
`Write` output during execution), all failing the same way:

1. **`MALOCALDEV.PatchContainer.Go()`** — a patch-runner that does `Write !, "[run] "_tClass_...` for
   every patch it evaluates.
2. **`%UnitTest.Manager.RunTest(...)`** — InterSystems' own stock test runner, which narrates test
   execution to the current device. Reproduced via a thin wrapper classmethod that called it directly.
3. **`CICD.ConfigureAll.Now()`** — a namespace-configuration runner that does `Write !, ">>> Namespace:
   "_tNS_" <<<"` and similar narration throughout, and also switches namespace (`ZN`) during execution.

All three are otherwise-ordinary classmethods, callable and correct when invoked from an IRIS terminal.
The common factor is `Write` output during the call — nothing else about them is unusual (no unusual
argument types, no long-running behavior beyond normal patch/config work).

## Workaround used

Wrap the target call in a throwaway classmethod that redirects the target's output through
`$$BeginCapture^%SYS.Capture(.tCookie)` / `$$EndCapture^%SYS.Capture(tCookie, .tCaptured)`, then
`Quit` a plain string built from the captured text plus the target's own return status — nothing is
`Write`n directly by the wrapper itself:

```objectscript
ClassMethod RunConfigureAllNow() As %String
{
    Set tSC = $$BeginCapture^%SYS.Capture(.tCookie)
    If $$$ISERR(tSC) Quit "BEGINCAPTURE FAILED: "_$System.Status.GetErrorText(tSC)

    Set tRunSC = ##class(CICD.ConfigureAll).Now()

    Set tSC = $$EndCapture^%SYS.Capture(tCookie, .tCaptured)
    If $$$ISERR(tSC) Quit "ENDCAPTURE FAILED: "_$System.Status.GetErrorText(tSC)

    Quit "Status: "_$System.Status.GetErrorText(tRunSC)_$Char(10)_"Console:"_$Char(10)_tCaptured
}
```

Calling `iris_execute_classmethod` against this wrapper (instead of the original target directly)
succeeds and returns a clean JSON envelope with the captured console text and status embedded in the
string return value. This confirms the target method itself runs correctly under the MCP server's
execution context — only the tool's own response when the *target* writes directly is broken.

This workaround requires writing and deploying a bespoke wrapper class per affected target method, which
is workable for one-off debugging but not something a caller should have to do routinely.

## Suggested fix

The classmethod-execution endpoint most likely builds its JSON response envelope on the same output
stream/device the target method's `Write` calls are also going to, so the two interleave and corrupt the
body into invalid JSON. Suggested direction: have the endpoint redirect/capture the target method's
current device internally before invoking it — functionally equivalent to the `%SYS.Capture` wrapper
above, but done server-side for every invocation — and surface any captured output as an additional
field in the JSON envelope (e.g. `"console": [...]`), the same way `iris_doc_compile`'s response already
returns a `console` array today. That existing precedent suggests the mechanism to reuse is already in
the codebase for at least one other tool.

## Related, currently-unsupported capability worth addressing in the same pass

While working around this, a related gap came up: **there is currently no way to pass a `ByRef`/`Output`
argument to a classmethod through this tool, or to retrieve its post-call value.** `iris_execute_classmethod`'s
schema only documents positional `args` as plain inputs. Several stock and project methods (e.g.
`MALOCALDEV.Test.PatchContainer.RunAll::RunStory11PrerequisiteAsstchTests(Output pSummary)`) rely on an
`Output` parameter for their real result rather than (or in addition to) their `%Status` return value —
today, the only way to get that information through the tool is to rewrite the target method to return
everything via its function return value instead, which isn't always practical or desirable for stock/
third-party methods. Worth considering alongside the `Write`-output fix, since both are about the same
underlying gap: the tool currently only round-trips a method's single return value, not everything else
a classmethod invocation can produce (device output, `Output`/`ByRef` parameters).
