# Bug report — `iris_execute_tests` abandons long runs client-side with no way to re-attach

**Component:** IRIS MCP Server Suite, `iris-dev` server, `iris_execute_tests` tool
**Reported:** 2026-09-10
**Severity:** Medium — no data loss, but it silently corrupts test-result attribution for any suite whose runtime exceeds the tool's internal timeout.

## Environment

| | |
| --- | --- |
| IRIS | IRIS for UNIX (Ubuntu Server LTS for ARM64 Containers) 2026.2 (Build 221U), Atelier API v8 |
| Instance id | `92989EE2-AB37-11F1-AE6A-769196E3B75A` |
| Namespace | `HSCUSTOM` |
| Server profile | `ocupilot-iris` (host port 52774) |
| Test class | `OcuPilot.Test.Demo` — 4–5 methods, one of which deliberately waits on the IRIS Task Manager daemon, so a single run legitimately takes **40–480 seconds** |

## Summary

`iris_execute_tests` returns

```
Error: Test execution timed out
```

to the caller while the corresponding `%UnitTest.Manager` run **continues executing server-side** and completes normally minutes later. The tool exposes no timeout parameter and returns no run identifier, so on receiving this error the caller cannot determine whether the run never started, is still in flight, or already finished — and has no way to re-attach to it.

The natural response to an apparent failure is to call again. That produces genuinely concurrent runs of the same test class, which is where real damage occurs (see *Consequences*).

## Observed behavior

1. **The client-side error fires well before the run ends.** A call against `OcuPilot.Test.Demo` returned `Error: Test execution timed out`. The client error arrived within roughly two minutes; `%UnitTest_Result` holds runs of that class with durations of **300 s and 480 s**. The run outlived the caller's view of it by several minutes.

2. **No run identifier is returned.** The success shape is `{total, passed, failed, skipped, details[]}`. The timeout path returns only the error string. There is nothing to poll, cancel, or correlate against `%UnitTest_Result`.

3. **No timeout control.** The tool's parameters are `target`, `level`, `namespace`, `server`. Nothing lets a caller raise the budget for a suite known to be slow, or request fire-and-forget with a handle.

4. **The error is indistinguishable from "nothing ran."** Nothing in the response says work was submitted and is still running. This is the crux: the failure mode is not the timeout itself, it is that the timeout is reported as though it were terminal.

5. **The long durations are the test's own, not a server cap.** Worth stating so it isn't chased as a red herring — the 480 s figure is this suite's own wait budget (a 300 s fixture wait plus a 180 s grace), and 90 s / 300 s runs correspond to earlier values of the same parameters. The tool is not truncating anything; the suite is genuinely that slow.

## Consequences

- **Duplicate submissions.** A caller that reads the error as terminal re-runs the suite. With no handle, this is the only available move.
- **Corrupted "latest run" attribution.** The documented way to read ground truth from `%UnitTest.Result` is to take `MAX($PIECE(ID,'||',1)+0)` per class. When two runs of a class are in flight, that picks whichever finished last — not the one the caller asked about. In our case the same class read green and red minutes apart depending purely on which sibling landed last, which cost several hours of misdirected debugging.
- **Shared-fixture races.** Concurrent runs of one class each execute `OnBeforeAllTests` / `OnAfterAllTests` against the same instance-wide fixtures (in our case a `%SYS.Task` row keyed by name and class). One run's teardown removes the object another run is mid-assertion on, producing failures that look like product defects and are not.

## Reproduction

1. Write a `%UnitTest.TestCase` class with a method that sleeps or polls for longer than the tool's internal timeout (roughly two minutes; our case waits on the Task Manager daemon for up to 480 s).
2. Call `iris_execute_tests` with `level: "class"` against it.
3. Observe `Error: Test execution timed out` returned to the caller.
4. Query the result global afterwards and observe the run completed normally, after the client had given up:

```sql
SELECT TOP 10 ID AS RunIdx, DateTime, Duration
FROM %UnitTest_Result.TestInstance
ORDER BY ID DESC
```

## What I could not establish

Stated explicitly so it isn't chased:

- **I have no evidence the tool itself retries or re-submits.** An earlier working hypothesis here was that one logical call fans out into several server-side runs. Reviewing run indices against timestamps, each of my own calls maps 1:1 to a single run. The concurrency I saw is fully explained by **two independent clients** (two agent sessions) submitting runs of the same class in the same window. Please do not spend time hunting for retry logic on my account.
- **I did not measure the timeout precisely.** Observed to fire in under about two minutes. Whether it is fixed, configurable server-side, or inherited from an HTTP client default, I do not know.
- **I did not determine whether `%UnitTest_Result.TestInstance.DateTime` records the start or the completion of a run.** It matters for reading the evidence table below, and the two readings imply different overlap windows.

## Suggested fixes, in the order I'd value them

1. **Never report a still-running job as a terminal error.** If the internal budget expires, return a distinct, non-error result that says the run was submitted and is still executing, and carries the `%UnitTest.Result` run index. That alone removes the incentive to re-submit and makes attribution correct.
2. **Return the run index on every path**, success or timeout, so callers can correlate with `%UnitTest_Result` rather than guessing at `MAX(runIdx)`.
3. **Expose a `timeout` parameter** (and/or an explicit async mode with a poll companion, mirroring how `iris_doc_compile` already offers `async` plus a job id). A suite that legitimately takes ten minutes should be expressible.
4. **Consider refusing to start a run of a target already in flight**, or at minimum reporting that one is. Concurrent runs of one class against shared instance fixtures are rarely what the caller wants, and are very hard to diagnose from the results afterwards.
5. **Document the timeout and this behavior** in the tool description. The current text — "Uses the Atelier async work queue for reliable execution" — reads as a promise that the caller does not need to think about long runs.

## Analysis addendum (2026-09-10, correct-course session — Mary)

Confirmed by source reading and live probes; corrections to the report where noted.

- **Timeout precisely measured:** `TEST_POLL_TIMEOUT = 120_000` ms, `packages/iris-dev-mcp/src/tools/execute.ts:137`, unchanged since the `/work` rewrite. Evidence matches: run 242 started 15:56:36 → client error ≈15:58:36 → run 243 submitted 15:58:49.
- **`DateTime` is the FINISH time** (`%UnitTest.Result.TestInstance` class doc); the run index is allocated at START (`%UnitTest.Manager.%OnNew` → `ReserveResultId` → `$i(^UnitTest.Result)`). The "out of order" indices are therefore expected: start-ordered indices, finish-ordered timestamps.
- **No retry/fan-out exists** — confirmed (`http-client.ts:256-261`: one 401 re-auth retry only).
- **Correction — `iris_doc_compile` is not a model to mirror:** its `async` mode returns no job id and there is no poll companion (`compile.ts:106-125`); its description claiming otherwise is a doc bug fixed in Story 36.1.
- **Re-attach is possible:** the queue node survives abandonment (`%Api.Atelier.v8:PollAsync` kills it only on a poll that observes completion). 10 orphaned unittest jobs found on this instance (run indices 203, 215, 234, 242, 245, 248, 249, 250, 253, 256), all finished. Run index recoverable today: `iris_global_get IRIS.TempAtelierAsyncQueue(<jobId>,"unittest","id")` (job 31797604 → 256).
- **Ledger:** already predicted by `34-6-CR-20` (b) (LOW, open); raised to MEDIUM and closed by Story 36.1.
- **Concurrency caveat (InterSystems code, not fixed):** Atelier predicts the run index (`v8.cls:730`) before the Manager allocates it (`Manager.cls:2833`), unlocked — near-simultaneous submissions can cross-attribute results.
- **Disposition:** Epic 36 — Story 36.1 (running-result contract, handles, `timeout`), Story 36.2 (`iris_test_status` re-attach/read/cancel).

## Resolved in Epic 36

Both root-cause remediation stories shipped: **Story 36.1** (committed `7f286ea`) fixed the contract
side — a wait-budget expiry now returns `isError:false`, `status:"running"`, the run's `jobId`/
`runIndex`, and a `partial` snapshot, so a still-running job is never mistaken for a failed one and
never prompts a re-submit. **Story 36.2** shipped the re-attach surface itself: `iris_test_status`
(`action: "poll"` re-attaches by `jobId` or reads by `runIndex`; `action: "cancel"`, default-disabled,
stops a run) closes the gap this report's recommendation #3/#4 named — a caller can now re-attach to
or deliberately stop the exact run this incident describes, instead of only observing it through the
manual `iris_global_get`/`iris_sql_execute` route.
