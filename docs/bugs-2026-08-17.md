# Bug report: `iris_doc_load` silently drops the package prefix when a literal directory sits between the base path and a trailing wildcard

**Component:** `iris-dev-mcp` MCP server, tool `iris_doc_load` — `extractBaseDir()` and `filePathToDocName()` in
`packages/iris-dev-mcp/src/tools/load.ts`.

**Reported by:** user-submitted Cline (VS Code extension) transcript, 2026-08-17, from an unrelated
machine/project (`/Users/jbrandt/clinetest`). This is not the tool's home repo — Cline was talking to a
deployed `iris-dev-mcp` server the same way any MCP client would.

## What happens

Calling `iris_doc_load` with a glob pattern whose only wildcard character sits in the *final* path
segment (e.g. a bare `*.cls`), with the package-name directory as a plain literal segment immediately
before it, uploads every matched file with **no package prefix at all** — silently. The upload step
reports success (`uploaded: N, failed: 0`); there is no validation or cross-check against the file's own
declared class name at `PUT` time. The failure only surfaces later, during compile, as an IRIS-side error
that gives no hint the real cause was upload-time path mapping.

## Repro

Cline sent well-formed, correct-looking arguments:

```json
{"path": "/Users/jbrandt/clinetest/src/ClineTest/*.cls", "compile": true, "namespace": "HSCUSTOM"}
```

Two files, `Wumpus.cls` and `WumpusCave.cls`, both declared as package `ClineTest` (e.g.
`Class ClineTest.Wumpus Extends ...`), living under `.../src/ClineTest/`.

Result:

```
Loaded 2/2 document(s) into namespace 'HSCUSTOM'. Compilation completed with errors.

{
  "total": 2,
  "uploaded": 2,
  "failed": 0,
  "compilationResult": {
    "success": false,
    "documents": ["Wumpus.cls", "WumpusCave.cls"],
    "errors": [
      {
        "document": "*",
        "error": "IRIS reported errors for POST /api/atelier/v8/HSCUSTOM/action/compile. Review the error details and correct the request. Details: خطأ #5351: Class 'User.Wumpus' does not exist."
      }
    ]
  }
}
```

The `documents` array already shows the defect: `Wumpus.cls` / `WumpusCave.cls`, not the intended
`ClineTest.Wumpus.cls` / `ClineTest.WumpusCave.cls`.

## Root cause

`extractBaseDir()` (`load.ts:82-101`) walks the glob pattern's `/`-delimited segments and stops at the
first segment containing a glob metacharacter (`*`, `?`, `{`, `[`). Every segment before that stop
point — including plain literal directory names — is folded into `baseDir`, which `filePathToDocName()`
(`load.ts:48-65`) then strips from each matched file's absolute path to produce the doc name.

For `/Users/jbrandt/clinetest/src/ClineTest/*.cls`, the wildcard only appears in the trailing `*.cls`
segment. `ClineTest` — the package directory — is a plain literal segment, so it gets folded into
`baseDir` along with everything before it:

```
baseDir = /Users/jbrandt/clinetest/src/ClineTest
```

Stripping that from `.../src/ClineTest/Wumpus.cls` leaves `Wumpus.cls` — an unqualified doc name with no
package. `PUT /doc/Wumpus.cls` succeeds regardless; nothing cross-checks it against the file's own
`Class ClineTest.Wumpus` declaration. At compile time, IRIS resolves the unqualified name via its
default-package fallback to `User`, doesn't find it there (the real class lives in `ClineTest`), and the
whole compile `POST` fails at the request level (`"document": "*"`) with
`Class 'User.Wumpus' does not exist` — an error that, read cold, gives no hint the actual defect is
upstream in how the doc name was derived from the glob pattern.

Workaround: write the pattern so the wildcard segment starts *before* the package directory, not after
it — `/Users/jbrandt/clinetest/src/**/*.cls` — so `ClineTest` survives as a path segment past `baseDir`.

This is not a new failure class. It matches project rule #17
(`.claude/rules/iris-objectscript-basics.md`: *"iris_doc_load requires a glob-prefixed path... a bare
file path collapses the class to User.\<stem\>"*), captured from an earlier incident. This transcript is a
second, independent repro on an unrelated machine and project, with zero warning surfaced to the caller
before the confusing IRIS-side failure — evidence this deserves an actual code fix rather than remaining
a documented workaround.

## Suggested fix

**Short-term (cheap, immediate):** after computing each uploaded `docName`, flag any that resolve with
zero package segments (no dot in the stem) during a bulk multi-file `.cls`/`.mac`/`.int` upload, and
surface a warning in the tool's response text *before* compile runs — e.g. *"N document(s) uploaded
without a package prefix — if unintended, check that your glob pattern's wildcard precedes the package
directory (use `**` rather than a trailing `*`)."* This turns a silent trap into an immediate, actionable
signal at upload time instead of a cryptic compile-time IRIS error three steps downstream.

**Long-term (structural):** stop deriving the doc name purely from glob-pattern shape. For
`.cls`/`.mac`/`.int`/`.inc` files, the file's own content already declares its identity
(`Class Foo.Bar Extends ...` / `ROUTINE Foo`) — parse that declared name and use it as the authoritative
doc name, or at minimum cross-check it against the path-derived name and refuse the upload with a clear
mismatch error naming both candidates, rather than uploading a mismatched doc silently. This makes the
tool correct-by-construction regardless of how the caller's glob happens to be shaped, removing the
path-inference heuristic as a source of silent failure entirely. Pair this with an optional explicit
`baseDir` parameter so programmatic callers (agents especially) can state the package root
deterministically instead of relying on glob-shape inference at all. CSP/slash-style docs (no embedded
class/routine name) keep path-derived naming as today, since there is no content identity to fall back
to.

## Impact

Any bulk `.cls`/`.mac`/`.int` upload where the caller's glob pattern places a literal package-name
directory immediately before a trailing single-segment wildcard (`*.ext`, as opposed to `**/*.ext`) is
affected — a very natural pattern to type when pointing at "this one class folder." The failure mode
gives no direct signal that path mapping is the cause; a caller unfamiliar with the tool's internal
`extractBaseDir` behavior would have to reason backward from an IRIS `User.<X> does not exist` error to
arrive at the real explanation, as happened here.
