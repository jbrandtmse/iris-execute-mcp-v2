- 48ad081: feat: the automatic install of the IRIS side is a setting, and the read-only preset turns it off (Story 45.2, sanction `S-45.2-read-only-no-install`, GitHub issue #1 point 3)
  - New variable `IRIS_AUTO_INSTALL` (`true` or `false`, any letter case; empty is unset) and a per-profile `autoInstall` field in `IRIS_PROFILES` (a JSON boolean). For each profile the first of these wins: the profile's own `autoInstall`, then `IRIS_AUTO_INSTALL`, then `IRIS_GOVERNANCE_PRESET=read-only` (which forces it off), then on. The `default` entry's value is never inherited, Server Manager profiles take the variable, and the governance file is not a channel.
  - With the install off the bootstrap sends reads only: no document upload, no compile, no `Configure`, `ConfigureMapping` or `EnsureUnitTestRoot`. Before, a server started with `IRIS_GOVERNANCE_PRESET=read-only` installed 35 classes, the `/api/executemcp/v2` web application, the `%ALL` namespace and mapping, and `^UnitTestRoot` on connect.

  - Upgrade note: after a release that changes the IRIS-side classes (its CHANGELOG says so in its IRIS side section, and the hash at the end of `BOOTSTRAP_VERSION` changes; 1.3.0 does), an instance that only read-only servers, or servers with the automatic install off, connect to refuses its custom-REST tools with `IRIS_SIDE_NOT_INSTALLED` until an operator upgrades the IRIS side once: one start with the automatic install on, or `zpm`. ### Patch Changes

- 38389cb: fix(data): actionable error when %Service_DocDB is disabled (Epic 35, Story 35.7 / 35-SWEEP-5)

  `%Service_DocDB` is disabled by default on IRIS, and all four DocDB tools (`iris_docdb_manage`, `iris_docdb_document`, `iris_docdb_find`, `iris_docdb_property`) previously failed with a bare `ERROR #822: Access Denied` and no path forward. The tools now detect this case on the error path — an `IrisApiError` carrying the locale-stable numeric `code: 822` (message text is never matched) triggers a single follow-up check of the live `%Service_DocDB` state, and when the service reads disabled the error becomes an actionable message naming the cause and BOTH remedies: the Management Portal (System Administration > Security > Services > %Service_DocDB), or `iris_service_manage` with `action="enable"` (itself governance-default-disabled, requiring an `IRIS_GOVERNANCE` override such as `{"global": {"iris_service_manage:enable": true}}`). When the service is enabled (a genuine privilege failure), when the state check itself fails, or when the error is not 822, the original error passes through unchanged. The four tool descriptions and the package README now document the prerequisite, and `tool_support.md` no longer claims the service is enabled by default.

- 04a566c: feat(execute): bound `iris_execute_command`/`iris_execute_classmethod` response payloads, make the epic gate fail closed, and make the zero-result guard machine-detectable (Story 34.6, pre-publish hardening)

  **Response payload ceiling (AC 34.6.1, `34-2-R2`/`34-3-R2`).** `output` on both `/command` and `/classmethod` is now capped at 32768 characters (`ExecuteMCPv2.Utils.OUTPUTCEILING`) — content beyond the ceiling is cut off and replaced with a structured, machine-detectable elision marker (`[IRIS-MCP-TRUNCATED ceiling=32768chars]` when the field had the whole budget; a field that follows another carries `ceiling=<N>chars` with `<N>` the budget that remained for it, so detect the marker by the stable `[IRIS-MCP-TRUNCATED` prefix, never the full literal), never a bare `...`. `truncated` folds this in alongside the pre-existing capture-overflow signal (only ever set, never cleared, so the two causes OR together). `iris_execute_classmethod`'s `byRefValues` gains its own combined 1000-node (`ExecuteMCPv2.Utils.BYREFNODECEILING`) / 32768-character budget shared across every marked position, surfaced via a new additive `byRefTruncated` boolean — reported separately from `truncated` since they describe different response fields. A cut-off node in `byRefValues` is marked `subscriptsTruncated: true`.

  The ceiling was picked from live measurement (Rule #36), not by feel: the CSP Gateway/HTTP transport tolerates multi-megabyte responses cleanly (tested clean to 3,000,000 characters over `/command`), so **this is explicitly not protection against a Web Gateway timeout or the target's own execution cost** (Rule #38) — the target has already fully run by the time the ceiling is applied. 32768 was chosen because a real, live MCP client (Claude Code CLI, this repo's own dev environment) was observed diverting a rendered tool result away from inline consumption once it reached 50,031 characters; 32768 stays safely under that measured boundary. **Superseded below (Story 34.7):** the ceiling was originally applied PER FIELD (`output`, `returnValue`, and the `byRefValues` budget each getting their own, so a response carrying all three at once could reach roughly three times this figure before JSON escaping) — this shape shipped only within this same pre-release development cycle and was replaced before the first publish by ONE shared budget across all three fields; see the "ONE shared response budget" section near the end of this changeset for the shipped behavior.

  **Back-compat (Rule #19), proven mechanically:** under-ceiling responses on both endpoints are byte-identical to today's shape (live HTTP + `%UnitTest` pins); `byRefTruncated` is additive and simply absent — never `false` — from a pre-34.6 envelope shape.

  **`returnValue` is now ALSO bounded (code-review finding CR-5, review-continuation pass).** The ceiling above covered `output` and `byRefValues` but not `returnValue` — the PRIMARY payload field on `/classmethod` — so a target returning a large string shipped fully unbounded, defeating the ceiling's own stated purpose (a live 1,000,000-character `returnValue` shipped with `truncated:false`). `returnValue` is now capped at the same 32768 characters with the same elision marker, flagged via a new additive `returnValueTruncated` boolean (symmetric with `truncated`/`byRefTruncated`, present — defaulted false — on both error envelopes too). Pinned at the REAL deployed `/classmethod` endpoint (a new leg in the epic-gate file, not a re-implementation), mutation-verified RED when the fix is removed. **Back-compat (Rule #19):** under-ceiling `returnValue` is byte-identical; `returnValueTruncated` is additive and absent (not `false`) from a pre-fix envelope.

  **The `byRefValues` byte budget no longer destroys small values with oversized markers (code-review finding CR-6, review-continuation pass — a defect this story itself introduced, not pre-existing).** Once one large `Output` value exhausted the shared byte budget, every later marked position was still truncated — and when the remaining budget was smaller than the ~37-character elision marker itself, that truncation replaced a small real value with a marker LARGER than the value it destroyed (live repro: `"42"`, `"hello"`, `"x"` became 37-character markers), pushing the total past the documented 32768-character budget. Fixed in two places: `ApplyOutputCeiling` now falls back to a plain, marker-less hard cut whenever the marker itself would not fit in the remaining budget (a result is never bigger than the ceiling it was given, nor bigger than the value it replaces), and the 20 top-level `byRefValues` positions now share the same budget pre-check the recursive subscript walk already had (`AddByRefPosition`) — a position is OMITTED from `byRefValues` entirely once the shared budget is already exhausted, rather than materialized as a misleading placeholder. Pinned at the REAL deployed endpoint with the exact review repro shape, mutation-verified RED when either half of the fix is removed.

  **The `byRefValues` character budget now charges subscript keys and OREF placeholders, not just leaf values (code review, cycle 2).** The budget above was decremented only by each leaf VALUE's length, so subscript KEYS and `<Object:...>` placeholders were emitted free — meaning the advertised 32768-character `byRefValues` budget did not actually bound `byRefValues`. Measured live: an `Output` array of 400 positions keyed by 900-character subscripts emitted **363,908 characters** with 32,368 of the budget still reported unspent and `byRefTruncated` still `false`; 400 OREF out-values emitted ~16,000 characters without touching the budget at all. A long-keyed `Output` array (file paths, URLs, composite keys) is an entirely idiomatic ObjectScript shape, so this was reachable by ordinary callers — the same unbounded-payload class as CR-5, one field over. Every emitted piece of content is now charged; the same 363,908-character case now emits 32,797 characters with `byRefTruncated: true`. The per-node JSON scaffolding (~25-30 characters per container node) is still not charged and is bounded instead by the 1000-node ceiling, which is now stated explicitly at every doc site rather than implied away.

  **The byRef elision contract is now stated in full (code review, cycle 2).** The tool description and README previously described a false dichotomy — a value that no longer fits is "either cut short with an elision marker … or omitted entirely". There is a third case the code has always produced and the story's own gate leg (e-4) pins as correct: when the remaining budget is positive but smaller than the ~40-character marker, the value is cut to a **plain unmarked prefix**. Both surfaces now describe all three outcomes and state plainly that in the unmarked case `byRefTruncated` is the only signal — so the absence of a marker must not be read as proof a byRef value is complete.

  **Non-ASCII request-body content — documented here, and FIXED in Story 34.8 before this release ships (code-review finding CR-7, review-continuation pass).** _(Superseded: see `request-body-utf8-decode-fix.md` in this same release — the defect described below was fixed in Story 34.8 rather than shipped as a Known Limitation. This entry is retained for provenance; both READMEs and the CHANGELOG describe the fixed behavior.)_ Every custom `ExecuteMCPv2.REST.*` handler's shared request-body parser (`ExecuteMCPv2.Utils.ReadRequestBody`, 14 handler classes / 46 call sites across all five servers) reads non-ASCII JSON content as if it were Latin-1, silently corrupting it on the way in — `HTTP 200`, no error, no flag — most directly affecting `iris_global_set`'s `value` (data corruption **at rest**), plus `iris_execute_command`'s `command` and `iris_execute_classmethod`'s `args`. Pre-existing across every epic and untouched by this story's actual code changes (Rule #52 scope discipline); a proper fix requires investigating IRIS's CSP request-body character-set negotiation. Per the code review's explicit ship/no-ship call, this is now documented prominently rather than shipped silently: a new "Known Limitations" note in both the suite README and `@iris-mcp/dev`'s own README, referencing ledger item `34-6-CR-7`.

  **Epic-gate hardening (AC 34.6.2/34.6.3, `34-4-R1`/`34-4-R3`, internal — not a published-package behavior change).** The `iris_execute_classmethod` epic-done gate's leg (d) previously asserted only that `%SYSTEM.Version.GetVersion()` returned a version-looking string — identical in every namespace, so a regression dropping the `namespace` parameter entirely would still pass. It now calls a target that echoes `$NAMESPACE` and asserts the value both equals the requested namespace and differs from the configured default (mutation-verified RED when `namespace` is dropped). Separately, the gate's fixture-availability probe previously collapsed any failure (credential fault, network error, licence issue) into the same "fixtures not deployed" verdict as a genuinely missing fixture; it now re-throws anything that is not a genuine "document not found" response. `IRIS_REQUIRE_LIVE=1` is now armed on `@iris-mcp/dev`'s own `prepublishOnly` npm/pnpm lifecycle hook, mechanically confirmed via `pnpm publish --dry-run` to abort packaging (before a tarball is ever produced) when IRIS is unreachable.

  **Zero-result guard machine-detectability (AC 34.6.4, `34-5-R1`, recorded Project Lead decision).** `iris_execute_tests`' zero-result guard (added in the prior Epic 34 story) previously returned content-only JSON with no `isError`/`structuredContent`, so a structured consumer reading `structuredContent.total` regressed from `0` to `undefined`, and an agent branching on `isError` recorded the call as a success. - eb75133: fix(execute): decode non-ASCII request-body content correctly instead of silently corrupting it (Story 34.8, ledger `34-6-CR-7`)

  **The defect.** Every custom `ExecuteMCPv2.REST.*` handler read its JSON request body through the shared `ExecuteMCPv2.Utils.ReadRequestBody` helper (14 handler classes, 46 call sites, spanning all five servers), which handed the raw POST body straight to `%DynamicObject.%FromJSON()` with no UTF-8 decode. Non-ASCII characters submitted through a request body arrived mis-decoded as their raw UTF-8 bytes read as Latin-1 — `é` (U+00E9) as two garbled characters, `世界` as six, an emoji as four — silently, with `HTTP 200` and no error or truncation flag. This affected `iris_execute_command`'s `command`, `iris_execute_classmethod`'s `args`, and — most seriously — `iris_global_set`'s `value`, where the corrupted text was written to the target global as genuine **data corruption at rest**. Content that originates server-side (e.g. a compiled class's literal source) was always unaffected; the defect was strictly on the inbound request-body path. Story 34.7 documented this as a Known Limitation rather than fix it before the first publish; the Project Lead elected to fix it before publishing rather than ship documented data corruption.

  **Root cause, live-probed (AC 34.8.1) rather than guessed.** `%request.GetMimeData("BODY")` is never populated for this project's plain `application/json` POSTs (multipart-only) — the primary branch in `ReadRequestBody` was dead in practice; every real call fell through to the `%request.Content` fallback, a `%CSP.BinaryStream` holding the raw, untranslated request bytes (confirmed byte-for-byte against a known UTF-8 encoding). `%request.CharSet` is empty because the TS client's `Content-Type: application/json` header carries no charset parameter, so no CSP-level charset negotiation ever applied.

  **The fix.** `ReadRequestBody` now routes the resolved stream through a new `ExecuteMCPv2.Utils.DecodeUtf8Stream`, which decodes the raw bytes as UTF-8 before handing the result to `%FromJSON`. Two properties, both required by the ACs and both mechanically pinned:
  - **Chunk-boundary safety.** Reads the stream in bounded chunks (1,000,000 raw bytes at a time) and detects, via a new `IncompleteUtf8TailLength` helper, whether the trailing 0-3 bytes of a chunk are the unfinished start of a multi-byte sequence — holding them back and prepending them to the next chunk rather than decoding a split sequence independently (the naive-per-chunk-`$ZCONVERT` trap). Live-verified with a deliberately tiny chunk size against content containing 2-, 3-, and 4-byte UTF-8 characters back to back, and swept across every possible chunk size for a representative fixture.
  - **Large-body safety, with two traps found live rather than assumed.** (1) `$ZCONVERT` given a stream OREF directly — rather than a materialized `%String` chunk — does not throw and does not decode: it silently stringifies the OREF itself. (2) A single `.Read(stream.Size)` call requesting an entire large stream's content in one shot does not reliably return it all: measured on a 49,000,000-byte stream, one such call silently returned only ~3.6 million characters, with **no exception of any kind** — never `<MAXSTRING>`, just quietly less data than requested. The fix reads in a `While 'stream.AtEnd` loop and accumulates DECODED output into a `%Stream.TmpCharacter` (never a growing `%String`), verified end-to-end at 49,000,000 raw bytes with zero exceptions and a correct content spot-check.

  **Back-compat (Rule #19), proven mechanically.** Pure-ASCII request-body content — every one of this suite's pre-existing ObjectScript command / classmethod-arg / global-value calls — is byte-for-byte identical before and after the fix (every ASCII code point 0-127 is already valid single-byte UTF-8, so the decode is a true no-op on ASCII). Pinned both at the ObjectScript unit level (`ExecuteMCPv2.Tests.Utf8DecodeTest`, 33 tests) and end-to-end against the real deployed `/command`/`/classmethod`/`/global` routes (`request-body-utf8-decode.test.ts`, 12 tests) — the latter also covers accented BMP, CJK, astral-plane emoji, mixed ASCII+non-ASCII, non-ASCII inside a `{byRef, value}` marker, a non-ASCII JSON key alongside real content, and the exact live reproduction string reported for this defect. Mutation-verified at both layers: reverting the fix reproduces the original mojibake live and turns both test files red; restoring it (byte-identical to the committed source) turns them green again.

  **QA follow-up fix, same story: malformed input could produce genuinely invalid UTF-8 on a response.** Adversarial QA testing found that `$ZCONVERT(...,"I","UTF8")` is lenient enough to decode a malformed 3-byte WTF-8/CESU-8 byte sequence (`0xED [0xA0-0xBF] [0x80-0xBF]` — never valid in conformant UTF-8, since RFC 3629 excludes the whole surrogate block from UTF-8) into a raw, unpaired UTF-16 surrogate code unit rather than rejecting it. The pre-Story-34.8 Latin-1 decode this replaced could never produce a surrogate from any input, so this was a new failure mode introduced by the UTF-8-aware decode, not a pre-existing one. Live-verified with a hand-crafted raw HTTP body (bypassing the sanitization any standard JSON+UTF-8 client, including this suite's own `IrisHttpClient`, always performs before such a byte pattern could reach the wire): an unpaired surrogate reaching a response was re-emitted by IRIS as genuinely invalid UTF-8 — a strict decoder threw on the actual response bytes, silently, under `HTTP 200`, no error, no truncation flag — the same underlying platform behavior Story 34.7's `SurrogateSafeCutLength` already guards against on the truncation/output side. Fixed with a new `ExecuteMCPv2.Utils.SanitizeUnpairedSurrogates` helper, applied to every decoded chunk, that substitutes `?` for any surrogate half without a valid pairing partner (matching `$ZCONVERT`'s own observed substitution for other invalid sequences) while leaving every genuine surrogate pair (real astral characters) completely untouched. Re-verified live after the fix: the same hand-crafted request now round-trips to a strictly-valid-UTF-8 response. Not reachable through any of this suite's own MCP tool clients — only through a hand-crafted raw HTTP body — but fixed rather than left as a new, undocumented gap, consistent with this epic's standing policy against shipping a silent-corruption path under `HTTP 200`.

  **The decoder is lenient, not validating — and that is now documented for users.** Beyond the unpaired-surrogate case above, two further malformed-input dispositions were determined live and pinned, and are stated in both READMEs' "Known Limitations" sections rather than left in code comments only: (1) any invalid byte sequence — an orphan continuation byte, an out-of-range lead byte, a truncated sequence at end of body — is replaced with a literal `?` under `HTTP 200` rather than rejected, and that `?` is indistinguishable from one the caller genuinely sent; (2) non-canonical **overlong** encodings are decoded rather than refused (e.g. the bytes `0xC0 0xAF` decode to `/`, which conformant UTF-8 per RFC 3629 forbids). (2) carries a **security note** now published in the suite README: overlong forms are a classic filter-bypass technique, so any proxy/WAF/gateway rule placed in front of these endpoints that inspects **raw bytes** for characters like `/`, `.`, or a quote can be bypassed by an overlong encoding that still decodes to the canonical character inside IRIS — such rules must normalize UTF-8 themselves. This matters because these endpoints execute arbitrary ObjectScript and write globals. Well-formed input is never affected by either behavior.

  **The fix is forward-only.** It corrects decoding for requests received after it is deployed; it does not repair data already written corrupted while the defect was live (e.g. a global populated via `iris_global_set` before upgrading). There is no automated repair tool for previously-corrupted data — documented explicitly in both READMEs' "Known Limitations" sections.

  No new tool, no new governance key, no tool-count change (Rule #31) — this is a fix to existing, already-governed request handling.

Additive `compile` (boolean, default false) and `flags` (string, only used when `compile` is true) parameters now mirror `iris_doc_load`: `compile: true` sends the native Atelier `flags` query param with the `c` compile qualifier folded in automatically when absent or explicitly negated (IRIS qualifiers are case-insensitive and `-c` negates — the fold guarantees an EFFECTIVE final `c`, so `-c` becomes `-cc`), so documents compile in the same call. When `compile` is omitted/false the request is byte-identical to the previous behavior (no `flags` param) and the response gains an honest note that the documents are NOT compiled, naming the remedy. Non-empty per-file `status` text from the load response (where IRIS reports compile errors while still answering HTTP 200) is now surfaced in the response text. Live-probed on IRIS 2026.1: `flags=ck`/`flags=c`/`flags=C` compile, `flags=k`/`flags=-c` and no flags do not; broken XML with `compile: true` surfaces `ERROR #5475` in the per-file status.

  **`iris_rest_manage:get` legacy routing (35-SWEEP-9).** `list` with `scope:"legacy"`/`"all"` returns hand-written `%CSP.REST` apps (e.g. `/api/executemcp/v2`), but `get` on such a name previously 404'd via the IRIS Management API with the CSP gateway's misleading "Check the IRIS web server configuration" text — a by-design scope boundary (the Mgmnt API covers spec-first apps only), not a misconfiguration. `get` now branches on the HTTP 404 STATUS (never the message text) and falls back to the legacy webapp list: a legacy name resolves to `{name, dispatchClass, namespace, swaggerSpec: null, explanation}` (`fullSpec` deliberately has no effect — no spec exists), and a name in neither scope fails with an accurate not-found naming BOTH scopes checked. Spec-first `get` is unchanged. `delete` remains spec-first-only: a legacy name fails with an explanation pointing at `iris_webapp_manage:delete`, which is the correct tool for removing a legacy web application.
