### Minor Changes

- 7f286ea: feat(execute): `iris_execute_tests` running-result contract, run handles, caller-controlled wait budget (Story 36.1)

  `iris_execute_tests` no longer reports a genuinely-still-running slow suite as a timeout error. When the wait budget expires with the Atelier job still executing, the tool now returns `isError: false` with `structuredContent.status: "running"`, the run's `jobId` and (once populated) `runIndex`/`runIndexSource`, and a `partial` snapshot of whatever has drained so far (`partial.total`/etc — never a top-level `total` a consumer could mistake for a final count). The response text leads with an unmistakable "Do NOT re-submit" instruction — re-submitting the same target starts a SECOND concurrent run against shared test fixtures, which is exactly the failure mode the first beta report (OcuPilot, 2026-09-10) hit: a multi-minute suite exceeded the tool's hard-coded 120-second budget, surfaced as a bare `Error: Test execution timed out` with no job handle, and the caller's only move (re-submit) created concurrent runs against shared fixtures.

  A completed run's envelope gains the same additive `status: "completed"`, `jobId`, `runIndex`, and `runIndexSource` (`"queue"` — captured from `IRIS.TempAtelierAsyncQueue(<jobId>,"unittest","id")` on a still-running poll via the pre-existing `iris_global_get` custom-REST route, no new ObjectScript — or `"counter"`, for a COMPLETED run only, when `^UnitTest.Result` read just before queueing vs. after completion moved by exactly 1 and the run drained result rows; otherwise `null` with a `runIndexNote` saying why) fields; existing `total`/`passed`/`failed`/`skipped`/`details` fields are byte-identical (Rule #19 — pinned by a `toEqual` minus-additive-fields test). A still-running result is never counter-attributed (its worker may not have allocated its index yet, so a delta of 1 could be another client's run). Every envelope — completed, running, the zero-result guard, "no job ID" and the polling-error catch — is built by ONE shared helper; a polling failure (HTTP error or network timeout) on an already-queued job returns its `jobId`, drained-so-far rows and the re-attach hint instead of losing the handle. The running `hint` carries the manual re-attach calls, live-run: the SQL joins `%UnitTest_Result.TestMethod` → `TestCase` → `TestSuite` → `TestInstance` (the only table with `InstanceIndex`) and selects `TestInstance.DateTime AS FinishedAt`, because those rows exist while the run still executes.

  A new optional `timeout` parameter (positive seconds) overrides the tool's wait budget per call; an operator may also set a process-wide default via `IRIS_TEST_TIMEOUT` (seconds; precedence `timeout` argument > `IRIS_TEST_TIMEOUT` > the existing 120-second default). Both are hard-capped at 3600 seconds, with `timeoutCapped: true` in the response when clamped (mirroring the `IRIS_SQL_MAX_ROWS`/`rowsCapped` precedent). `@iris-mcp/shared`'s `IrisConnectionConfig` gains the additive, optional `testTimeoutMs` field feeding this — `undefined` when `IRIS_TEST_TIMEOUT` is unset, matching `sqlTimeoutMs`'s existing convention exactly — and `mergeProfile` inherits it into every named profile (like `sqlTimeoutMs`), so the knob is not inert on calls that target a named `server` profile.

  Three narrow pre-existing defects in the same handler (ledger `34-5-R2`/`34-5-R3`/`34-5-R4`, carried since Story 34.5) were closed alongside this fix since they live in the exact code this story rewrites:
  - A malformed `level: "method"` target (more than one `:` separator, or an empty class segment before `:`) now returns an explicit, distinct error instead of silently mis-parsing. The pre-existing missing-colon and trailing-colon parse edges are UNCHANGED.
  - A test method named literally `Test` is now counted and its result restored correctly, both at class level and when targeted directly by name — previously a truthiness check on the (post-prefix-stripping, potentially empty-string) method name silently dropped it and could collide with the class-summary accumulator key. Verified live: BOTH the return leg and the Atelier request-leg filter (`methods: [""]`) work correctly once the return-leg truthiness bug is fixed — the Atelier endpoint's `methods` filter CAN target a method named exactly `Test`; the earlier "matches nothing" observation was itself a symptom of the return-leg bug, not a server-side limitation.
  - At `level: "method"`, a drained result whose restored method name does not match what was requested (the Atelier endpoint's `Test`-prefix-stripped wire filter is many-to-one — `Class:Validate` and `Class:TestValidate` both resolve to the same filter) now carries an additive `methodMismatchWarning` field naming the mismatch, rather than silently reporting a normal-looking passing result for a target that does not exist under the name the caller typed.

  `iris_doc_compile`'s `async` parameter description is also corrected: it promised "a job ID for polling" that the tool does not return (it returns `{mode: "async", docs, response}` immediately, with no poll companion route) — the description now states what is actually returned.

  **Testability seam:** an injectable `now`/`sleep` clock pair (`TestClock`, exported alongside a `createExecuteTestsHandler(clock?)` factory) lets the running-branch and handle-capture logic be pinned without burning wall-clock time — the first such seam in this repo, chosen over `vi.useFakeTimers()` for its smaller footprint. `executeTestsTool.handler` is `createExecuteTestsHandler()` with no argument (the real clock), so production behavior is unaffected.

  **Back-compat (Rule #19):** no new tool, action key, or governance key — `iris_execute_tests` keeps its existing bare (no-`action`) `write` classification, its default-ENABLED state (a grandfathered frozen-baseline member), and its frozen Epic-14 governance-baseline membership (`1e62c5ad5bf7`, 141 keys, unchanged). The three pre-existing accumulate-every-drain poll-loop regression tests pass with their test bodies and assertions byte-identical — only the describe-level mock plumbing now routes the new `/global` reads to their own mock — and are mutation-proven to still fail on both historical truncation shapes (first-drain-only, last-drain-only).

- 689f785: feat: iris_doc_get reads a line range (Story 38.2)

  `@iris-mcp/dev` (minor): `iris_doc_get` takes optional `startLine` and `endLine` (1-based, inclusive). A ranged read
  returns the lines in the `cat -n` layout (the number right-aligned in 6 columns, a tab, then the line exactly), plus
  `totalLines` and the document's version timestamp `ts`; an `endLine` past the end is clamped to the last line. Use it for

  so are `startLine` after `endLine`, `startLine` past the last line and an unreadable document. Each error says how to
  fix it. With neither parameter the request and the result are unchanged. The `metadataOnly` description now names `etag`.

  `@iris-mcp/shared` (minor): the line utility exports `documentLines`, `linesInRange`, `formatNumberedLines` and
  `NUMBERED_LINE_WIDTH`. `atelierDocStatusError` is unchanged; its documentation now covers any Atelier `/doc` result.

  returns `{ exists, name, etag }` without the never-filled `timestamp` key.

  `@iris-mcp/shared` (minor): adds the refusal-code catalog (`REFUSAL_CODES`, `refusalResult`, `RefusalCode`,
  `RefusalResult`) and the Storage-drop guard (`isClassDocument`, `storageDefinitionNames`, `droppedStorageDefinitions`,
  `storageDroppedRefusal`). The governance denial result is byte-identical.

- a7adcf9: feat(test-status): `iris_test_status` companion tool — re-attach, read-by-runIndex, cancel (Story 36.2)

  Epic 36's only new tool (dev 28 → 29): the re-attach/read/cancel companion Story 36.1 documented as a seam and this story ships. Re-attach to a run `iris_execute_tests` reported `status: "running"` for (or that your own client abandoned) instead of re-submitting the same target, which starts a SECOND concurrent run against shared fixtures.

  `action: "poll"` (read, enabled by default) accepts `jobId` and/or `runIndex`. By `jobId`: the queue node's run index is read BEFORE any poll that could be terminal (a terminal poll — or a `cancel` — consumes it, probe (b)); while `Retry-After` is present it returns the SAME `status: "running"` shape `iris_execute_tests` builds (through the identical shared `testRunEnvelope` helper, exported and reused rather than copied — Rule #52), with `partial` carrying THIS poll's DELTA drain only, never cumulative across separate calls. Once finished, the completed envelope is built AUTHORITATIVELY from `%UnitTest_Result` by exact `InstanceIndex` (`runIndexSource: "result-table"`) — never from a single drain alone: an earlier `iris_execute_tests` "running" response may already have consumed some rows, which never reappear (probe (d)). A `jobId` Atelier no longer recognizes (HTTP 404) falls back to a supplied `runIndex`, else reports a clear not-found result naming that fallback. By `runIndex` alone: `status: "completed"` (the same SQL path) once `TestInstance.DateTime` is set, or `status: "unfinished"` when it is not — the result table alone cannot distinguish a still-running job from a cancelled/crashed one (a cancelled run's row never finishes, probe (e)), so `unfinished` carries interim rows only under `partial`, each explicitly labelled `"in-progress"` and excluded from the counts (never reported as a pass — a mid-run `TestMethod` row reads `Status 1`/`Duration 0` before the method actually finishes, the trap the Story 36.1 review found in the manual SQL route). A `jobId` whose queue node is gone AND whose `runIndex` shows unfinished is reported `status: "abandoned"`.

  `action: "cancel"` (write, DEFAULT-DISABLED — enable via `IRIS_GOVERNANCE`, e.g. `{"global":{"iris_test_status:cancel":true}}`) stops a RUNNING job (`DELETE /work/{jobId}`, reading the queue node's run index BEFORE the delete — the only chance to) and reports the OBSERVED outcome, never assumed: `status: "cancelled"` with what was actually seen (queue entry gone; result row never finalized), or, when the job had ALREADY finished but was never drained, `status: "completed"` with a note that cancelling discarded only the queue entry and results are preserved at that `runIndex`. `cancel` requires `jobId` (there is no way to cancel by `runIndex` alone — the Atelier work-queue `DELETE` route operates on the job id).

  A Task 1 live probe found the normalization this story's SQL-path builder depends on: `%UnitTest_Result.TestMethod.Duration` is recorded in SECONDS (its class doc says so) while the Atelier drain's `duration` field (what `iris_execute_tests`'s `details` already carries) is in MILLISECONDS — verified live with a real 10-second `Hang` (drain `10009.384` vs. SQL `10.009384`, an exact ×1000). The SQL-path builder converts it to the drain's exact milliseconds (an integer-microsecond scale then one division — a plain float `* 1000` is not exact), and also carries the drain's method-level error text (e.g. a thrown exception) and row order, so its `completed` envelope is VALUE-identical to the drain-path one for the same run — pinned by unit tests on live captures and by the live capstone's exact drain-path equality leg (`ExecuteMCPv2.QAFixtures.DeltaDrainTest`). A finished run with no method-level results returns the same `isError: true` zero-result guard `iris_execute_tests` does.

  `iris_execute_tests`'s own `hint` (on a `running`/error result) and description now name `iris_test_status` as the primary re-attach route, alongside the manual `iris_global_get` + `iris_sql_execute` route that still works in every preset (including `core`, which does not include the new tool — Lead decision L-2: `core` is already at its 13-runtime-tool ceiling).

  **Governance:** two new post-foundation keys, `iris_test_status:poll` (read, enabled) and `iris_test_status:cancel` (write, disabled) — the frozen Epic-14 baseline (`1e62c5ad5bf7`, 141 keys) is unchanged (203 live / 62 post-foundation). **Visibility:** `developer`-preset include, `core`-preset exclude; NOT a `TOOL_PAIRS` member. - 8de37a3: fix(global): `subscripts` is now always literal data, never evaluated as code (Story 36.4, ledger `36-2-CR-1`, HIGH)

  **The defect.** `ExecuteMCPv2.REST.Global:BuildGlobalRef` wrapped a caller-supplied string subscript in a quoted literal WITHOUT doubling a quote character it contained, then the handlers evaluated the resulting reference by ObjectScript indirection (`$Get(@tRef)`/`$Data(@tRef)` for `iris_global_get`, `Set @tRef` for `iris_global_set`, `Kill @tRef` for `iris_global_kill`). A `subscripts` value containing a quote could close the literal early and the rest of the value ran as ObjectScript code. Present since the `/global` handler shipped (Story 3.2, 2026-04-06). Because `iris_global_get` is READ-classified and default-enabled, this was reachable under `IRIS_GOVERNANCE_PRESET=read-only` and any policy that disables writes — the read-only safety preset did not, in fact, mean read-only.

  **The fix.** `BuildGlobalRef` (shared by all three handlers) now emits every subscript as a canonical number or as ONE escaped string literal. - eb75133: fix(execute): decode non-ASCII request-body content correctly instead of silently corrupting it (Story 34.8, ledger `34-6-CR-7`)

  **The defect.** Every custom `ExecuteMCPv2.REST.*` handler read its JSON request body through the shared `ExecuteMCPv2.Utils.ReadRequestBody` helper (14 handler classes, 46 call sites, spanning all five servers), which handed the raw POST body straight to `%DynamicObject.%FromJSON()` with no UTF-8 decode. Non-ASCII characters submitted through a request body arrived mis-decoded as their raw UTF-8 bytes read as Latin-1 — `é` (U+00E9) as two garbled characters, `世界` as six, an emoji as four — silently, with `HTTP 200` and no error or truncation flag. This affected `iris_execute_command`'s `command`, `iris_execute_classmethod`'s `args`, and — most seriously — `iris_global_set`'s `value`, where the corrupted text was written to the target global as genuine **data corruption at rest**. Content that originates server-side (e.g. a compiled class's literal source) was always unaffected; the defect was strictly on the inbound request-body path. Story 34.7 documented this as a Known Limitation rather than fix it before the first publish; the Project Lead elected to fix it before publishing rather than ship documented data corruption.

  **Root cause, live-probed (AC 34.8.1) rather than guessed.** `%request.GetMimeData("BODY")` is never populated for this project's plain `application/json` POSTs (multipart-only) — the primary branch in `ReadRequestBody` was dead in practice; every real call fell through to the `%request.Content` fallback, a `%CSP.BinaryStream` holding the raw, untranslated request bytes (confirmed byte-for-byte against a known UTF-8 encoding). `%request.CharSet` is empty because the TS client's `Content-Type: application/json` header carries no charset parameter, so no CSP-level charset negotiation ever applied.

  **The fix.** `ReadRequestBody` now routes the resolved stream through a new `ExecuteMCPv2.Utils.DecodeUtf8Stream`, which decodes the raw bytes as UTF-8 before handing the result to `%FromJSON`. Two properties, both required by the ACs and both mechanically pinned:
  - **Chunk-boundary safety.** Reads the stream in bounded chunks (1,000,000 raw bytes at a time) and detects, via a new `IncompleteUtf8TailLength` helper, whether the trailing 0-3 bytes of a chunk are the unfinished start of a multi-byte sequence — holding them back and prepending them to the next chunk rather than decoding a split sequence independently (the naive-per-chunk-`$ZCONVERT` trap). Live-verified with a deliberately tiny chunk size against content containing 2-, 3-, and 4-byte UTF-8 characters back to back, and swept across every possible chunk size for a representative fixture.
  - **Large-body safety, with two traps found live rather than assumed.** (1) `$ZCONVERT` given a stream OREF directly — rather than a materialized `%String` chunk — does not throw and does not decode: it silently stringifies the OREF itself. (2) A single `.Read(stream.Size)` call requesting an entire large stream's content in one shot does not reliably return it all: measured on a 49,000,000-byte stream, one such call silently returned only ~3.6 million characters, with **no exception of any kind** — never `<MAXSTRING>`, just quietly less data than requested. The fix reads in a `While 'stream.AtEnd` loop and accumulates DECODED output into a `%Stream.TmpCharacter` (never a growing `%String`), verified end-to-end at 49,000,000 raw bytes with zero exceptions and a correct content spot-check.

  **Back-compat (Rule #19), proven mechanically.** Pure-ASCII request-body content — every one of this suite's pre-existing ObjectScript command / classmethod-arg / global-value calls — is byte-for-byte identical before and after the fix (every ASCII code point 0-127 is already valid single-byte UTF-8, so the decode is a true no-op on ASCII). Pinned both at the ObjectScript unit level (`ExecuteMCPv2.Tests.Utf8DecodeTest`, 33 tests) and end-to-end against the real deployed `/command`/`/classmethod`/`/global` routes (`request-body-utf8-decode.test.ts`, 12 tests) — the latter also covers accented BMP, CJK, astral-plane emoji, mixed ASCII+non-ASCII, non-ASCII inside a `{byRef, value}` marker, a non-ASCII JSON key alongside real content, and the exact live reproduction string reported for this defect. Mutation-verified at both layers: reverting the fix reproduces the original mojibake live and turns both test files red; restoring it (byte-identical to the committed source) turns them green again.

  **QA follow-up fix, same story: malformed input could produce genuinely invalid UTF-8 on a response.** Adversarial QA testing found that `$ZCONVERT(...,"I","UTF8")` is lenient enough to decode a malformed 3-byte WTF-8/CESU-8 byte sequence (`0xED [0xA0-0xBF] [0x80-0xBF]` — never valid in conformant UTF-8, since RFC 3629 excludes the whole surrogate block from UTF-8) into a raw, unpaired UTF-16 surrogate code unit rather than rejecting it. The pre-Story-34.8 Latin-1 decode this replaced could never produce a surrogate from any input, so this was a new failure mode introduced by the UTF-8-aware decode, not a pre-existing one. Live-verified with a hand-crafted raw HTTP body (bypassing the sanitization any standard JSON+UTF-8 client, including this suite's own `IrisHttpClient`, always performs before such a byte pattern could reach the wire): an unpaired surrogate reaching a response was re-emitted by IRIS as genuinely invalid UTF-8 — a strict decoder threw on the actual response bytes, silently, under `HTTP 200`, no error, no truncation flag — the same underlying platform behavior Story 34.7's `SurrogateSafeCutLength` already guards against on the truncation/output side. Fixed with a new `ExecuteMCPv2.Utils.SanitizeUnpairedSurrogates` helper, applied to every decoded chunk, that substitutes `?` for any surrogate half without a valid pairing partner (matching `$ZCONVERT`'s own observed substitution for other invalid sequences) while leaving every genuine surrogate pair (real astral characters) completely untouched. Re-verified live after the fix: the same hand-crafted request now round-trips to a strictly-valid-UTF-8 response. Not reachable through any of this suite's own MCP tool clients — only through a hand-crafted raw HTTP body — but fixed rather than left as a new, undocumented gap, consistent with this epic's standing policy against shipping a silent-corruption path under `HTTP 200`.

  **The decoder is lenient, not validating — and that is now documented for users.** Beyond the unpaired-surrogate case above, two further malformed-input dispositions were determined live and pinned, and are stated in both READMEs' "Known Limitations" sections rather than left in code comments only: (1) any invalid byte sequence — an orphan continuation byte, an out-of-range lead byte, a truncated sequence at end of body — is replaced with a literal `?` under `HTTP 200` rather than rejected, and that `?` is indistinguishable from one the caller genuinely sent; (2) non-canonical **overlong** encodings are decoded rather than refused (e.g. the bytes `0xC0 0xAF` decode to `/`, which conformant UTF-8 per RFC 3629 forbids). (2) carries a **security note** now published in the suite README: overlong forms are a classic filter-bypass technique, so any proxy/WAF/gateway rule placed in front of these endpoints that inspects **raw bytes** for characters like `/`, `.`, or a quote can be bypassed by an overlong encoding that still decodes to the canonical character inside IRIS — such rules must normalize UTF-8 themselves. This matters because these endpoints execute arbitrary ObjectScript and write globals. Well-formed input is never affected by either behavior.

  **The fix is forward-only.** It corrects decoding for requests received after it is deployed; it does not repair data already written corrupted while the defect was live (e.g. a global populated via `iris_global_set` before upgrading). There is no automated repair tool for previously-corrupted data — documented explicitly in both READMEs' "Known Limitations" sections.

  No new tool, no new governance key, no tool-count change (Rule #31) — this is a fix to existing, already-governed request handling.
